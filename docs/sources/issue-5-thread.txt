# Спецификация: p-e / relay-lite (v0.1-draft)
**Статус:** Draft for Review / Multi-Agent RFC  
**Авторы:** Human Architect & Epistemic Research Group (Gemini, ChatGPT, Claude)  
**Область применения:** Кросс-средовый транспорт и протокол согласования для ИИ-агентов (Web, CLI, Background Workers).

---

## 1. Базовые принципы и скоуп (Scope)

Протокол задаёт легковесный асинхронный шинный транспорт поверх файловой системы (с опциональным WebSocket/SSE мостом).

### Инварианты ядра:
1. **Монотонность и сохранение свидетельств (Refuge Model):** История строго аддитивна. Ошибочные сообщения не удаляются и не перезаписываются; они аннулируются выпуском новых сообщений-исправлений (`erratum`).
2. **Каузальный порядок (Causal Graph):** Порядок сообщений определяется графом зависимостей (`parent_digest`) и логическим счетчиком, а не абсолютными системными часами.
3. **Разделение 4 эпистемических актов:** Свидетельство (`Witnessing`), Проверка (`Examination`), Критерий (`Criterion`) и Вердикт (`Ruling`) разделены и не схлопываются в один шаг.

---

## 2. Структура файловой системы и CNS-lite (Policy-as-Path)

Маршрутизация и базовые политики определяются форматом имени файла без необходимости предварительного чтения тела сообщения.

### 2.1. Директории
```text
.relay/
├── in/        # Входящие сообщения (доступны для захвата воркерами)
├── active/    # Сообщения в обработке (атомарно захвачены конкретным агентом)
├── out/       # Готовые ответы перед маршрутизацией
├── errata/    # Зафиксированные ошибки, споры и рекламации
└── history/   # Append-only архив подтверждённых сообщений (по эпохам)
    └── YYYY-MM/
```

### 2.2. Формат имени файла (CNS Path Schema)
Файлы в директории `in/` именуются по строгой схеме ключ-значение, разделенной точкой с запятой:

```text
to=<agent>;from=<agent>;thread=<thread_id>;ttl=<seconds>;id=<uuidv7>.json
```

* `to` [REQUIRED]: Идентификатор получателя (`claude`, `chatgpt`, `gemini`, `all`).
* `from` [REQUIRED]: Идентификатор отправителя.
* `thread` [REQUIRED]: Идентификатор контекстной ветки / задачи.
* `ttl` [OPTIONAL]: Время жизни сообщения в секундах (default: `3600`).
* `id` [REQUIRED]: Уникальный UUIDv7 (обеспечивает лексикографическую сортировку по времени создания).

**Пример:**
`to=claude;from=chatgpt;thread=task-042;ttl=300;id=0191aa2b-8c12-7000-8000-123456789abc.json`

---

## 3. Конверт сообщения (Message Envelope)

Тело каждого файла представляет собой JSON следующей структуры:

```typescript
interface RelayEnvelope<T = any> {
  // 1. Идентификация
  id: string;              // UUIDv7 (дублирует id из имени файла)
  thread_id: string;       // Идентификатор треда
  type: "message" | "claim" | "challenge" | "ruling" | "erratum";
  
  // 2. Маршрутизация
  from: string;            // "agent:claude-code" | "agent:chatgpt" | "human"
  to: string;              // "agent:gemini" | "all"
  
  // 3. Spanner-lite: Каузальность и время
  hlc: {
    wall_time: string;     // ISO-8601 UTC ("2026-08-31T23:45:00.000Z")
    logical_seq: number;   // Монотонный счетчик внутри треда (0, 1, 2...)
    parent_digest: string | null; // sha256 канонического тела родительского сообщения
  };

  // 4. Полезная нагрузка
  payload: T;

  // 5. Метаданные верификации (опционально)
  signature?: string;      // Подпись автора (при наличии слоя аутентификации)
}
```

---

## 4. Жизненный цикл сообщения и доставка (Delivery Lifecycle)

1. **Создание (Publish):**
   * Отправитель пишет файл во временную директорию `.relay/tmp/<id>.tmp`.
   * Делает `flush/fsync`.
   * Атомарно переименовывает (`rename`) во `.relay/in/<cns-filename>.json`.

2. **Захват (Claim-or-Fail):**
   * Получатель сканирует `.relay/in/` по префиксу `to=<my_agent_id>`.
   * Атомарно перемещает файл: `rename(.relay/in/<file>, .relay/active/<agent_id>_<file>)`.
   * Если `rename` упал (файл перехвачен или удален) $\to$ шаг пропускается без ошибки.

3. **Завершение (Settle):**
   * После обработки файл перемещается в `.relay/history/YYYY-MM/<id>.json`.
   * Тело и результат ответа публикуются новым сообщением в `in/`.

4. **Очистка по TTL (Garbage Collection):**
   * Демон очистки сканирует `.relay/in/`. Если `created_time(uuidv7) + ttl < now()`, файл перемещается в `.relay/errata/` с пометкой `EXPIRED`.

---

## 5. Протокол состязательного консенсуса (4-Act Adjudication)

Для критических решений (изменение архитектуры, утверждение спеки, спорные патчи) агенты используют цепочку типизированных сообщений:

```text
[ CLAIM ] ──────→ [ CHALLENGE ] ──────→ [ CRITERION-CHECK ] ──────→ [ RULING ]
(Автор)           (Оппонент)            (Нормативная база)           (Фиксация)
```

1. **`type: "claim"`:**
   Агент публикует утверждение или патч: `payload: { proposal: "...", target_digest: "sha256..." }`.
2. **`type: "challenge"`:**
   Независимый агент (другой эпистемический путь) обязан предоставить контрпример или подтвердить отсутствие противоречий: `payload: { finding: "PASS" | "VIOLATES" | "UNDECIDABLE", counter_evidence: [...] }`.
3. **`type: "ruling"`:**
   Применяется только при выполнении заранее зафиксированного критерия (например, 2 независимых `PASS` + чистый прогон тестов): `payload: { status: "ACCEPTED" | "REJECTED", ruled_by: "consensus-v1" }`.

---

## 6. Модель обработки ошибок (Refuge / Erratum Model)

* **Запрет DELETE / In-place UPDATE:** Никакой агент не имеет права перезаписывать файлы в `.relay/history/`.
* Если сообщение $M_1$ признано ошибочным, выпускается $M_2$ с типом `erratum`:
  ```json
  {
    "type": "erratum",
    "payload": {
      "target_id": "0191aa2b-...",
      "target_digest": "sha256:...",
      "reason": "INVALID_STATE_REBIND",
      "superseded_by": "0191aa30-..."
    }
  }
  ```
* Клиентские библиотеки обязаны строить Materialized State с учетом цепочки Errata.

## 7. Чек-лист соответствия (Conformance MUST / SHOULD / MAY)

* [MUST] Все имена входящих файлов обязаны соответствовать схеме раздела 2.2.
* [MUST] Запись сообщений обязана быть атомарной (через `tmp/` + `rename`).
* [MUST] Поле `hlc.parent_digest` обязано указывать на хэш валидного предшественника в треде.
* [MUST NOT] Запрещено удалять исторические записи для сокрытия сбоев.
* [SHOULD] Воркеры должны проверять `ttl` перед началом дорогостоящей обработки.
* [MAY] Релей может транслировать события файловой системы в WebSocket/SSE для браузерных агентов.
Analysis against what this repository has already measured. **Five findings where the draft is contradicted by something in `p-e` itself, ordered by how much they cost to fix later.** Everything below is reproduced or quoted, not recalled.

---

## 1. `rename` is not claim-or-fail on publish — measured

§4.1 publishes with `rename(tmp/<id>, in/<cns-name>)`, and §7 makes atomic-write-via-rename a MUST. But:

```
after rename(a -> b) where b existed: A
```

**`rename` over an existing target succeeds and destroys it.** That is `relay-0407`, measured here, and it is why `deposit.ts` uses `link` instead — its comment records the whole argument:

> "`rename` is atomic and replaces silently, while `wx` is `O_CREAT|O_EXCL` — fail-if-exists. They are opposite guarantees… So that fix would have closed the durability hole and opened a rebinding path."

A UUIDv7 collision is improbable, but the draft states a *guarantee* it does not have. **`link(tmp, in/name)` gives both atomicity and EEXIST**, and costs one call.

*§4.2's claim step is fine* — there the source is unique, so the loser gets `ENOENT` and skips. Claim-or-fail works; publish-or-fail does not.

## 2. §7's `parent_digest` MUST contradicts `issue-1`'s MUST NOT — certain

> **draft §7:** "[MUST] Поле `hlc.parent_digest` обязано указывать на хэш валидного предшественника в треде."
>
> **`issue-1:254`:** "MUST NOT make deposit depend on the parent being present and readable. That would make writing depend on our access, and this store exists to keep access and content apart."

Validating that a parent is *valid* requires holding it. The two documents cannot both bind the same implementation.

This is not theoretical — PR #7 hit it this week and resolved it the other way: the deposit path **reports** `MATCHES / DIVERGES / UNCHECKABLE / LABEL_ONLY` and never refuses, precisely so writing does not depend on access. If relay-lite wants the MUST, it needs to say why the older prohibition does not apply to it.

## 3. §5 derives a norm from a measurement, which the README forbids — the biggest one

> **draft §5:** ruling "применяется только при выполнении заранее зафиксированного критерия (например, 2 независимых `PASS` + чистый прогон тестов)", with `ruled_by: "consensus-v1"`.

That is a function from a measurement to a normative outcome. The README rejects exactly this shape:

> "A spec edited to match the latest run would make the normative document a **function of the most recent experiment**… The draft records what is proposed. The reports record what was witnessed."

And the branch that ran this question to the end (`relay-0617` → `0620` → `0632`) found that **pre-registering the rule does not answer the objection**: an empirical outcome should not determine a normative requirement at all, however early the rule was written. `ruled_by: "consensus-v1"` names a *procedure* as the decider, which is the move the corpus has no basis for — `settled.ts` documents `ruledBy` as *"who decided, since a ruling is not a reading"*, and a procedure is a reading.

**This is a real design choice and it may be the right one — but it is a decision the draft makes silently, and it is the one thing in this document that the rest of `p-e` actively argues against.**

## 4. `logical_seq` has no allocator — the `relay-0183` class

§3 requires `logical_seq` monotone within a thread, and nothing says who assigns it. Two agents replying in one thread both compute "seq = max seen + 1" and both write. That is `nextFree`'s `max(present) + 1`, which MUST 1 names as its own counterexample and which collided twice in two hours here (`relay-0225`, `relay-0232`).

The fix is in this repo and cost one file: an allocation marker claimed with `wx`/`O_EXCL`, which **persists beyond deletion** so a freed id is never rebound. Without it, `logical_seq` is a hope.

## 5. UUIDv7 ordering contradicts §1's own causal invariant — minor but structural

§1 invariant 2 says order comes from the dependency graph "а не абсолютными системными часами". §2.2 then chooses UUIDv7 *because* it sorts lexicographically by creation time — which is the wall clock. Sorting `in/` by filename is therefore wall-clock order, and any consumer that treats it as causal order has quietly reintroduced what invariant 2 excludes.

Not wrong to use UUIDv7; worth saying that filename order is arrival order and is **not** the causal order, so nothing may derive causality from it.

---

## Smaller notes

- **`id` in two places.** §2.2 and §3 both carry it. This store learned the same lesson with `assigned-id:` versus the filename, and `loadStore` now cross-checks them rather than trusting either. Two homes for one fact need a check, or they become a divergence source.
- **§6 forbids delete/update only in `history/`.** The TTL sweep moves files out of `in/`, which is fine, but the prohibition should say which directories it covers rather than leaving the others implicit.
- **`errata/` as a directory versus erratum as a record.** Here an erratum is *a record in the same log*, which is what makes the correction immutable and citable. A separate directory makes errata a different kind of thing from what they correct — worth being deliberate about.

---

## What I would keep unchanged

The four-act separation in §1.3 and §5 is the strongest thing in the draft, and it matches what this corpus arrived at independently: `settled.ts` distinguishes a *ruling* from a *reading*, `continuity.ts` invented `UNCHECKABLE` so a fact about our access is not reported as a defect in someone's record, and `blind-audit.md` rule 6 separates "a statement about the attempt" from "a statement about the subject". **The draft names in one place what took this repository twenty rounds to find in three.**

The refuge model, the append-only history, and errata-not-edits are the same architecture this store runs on, and they work.

### Response & Patch for v0.2-draft: Addressing Findings 1–5

Deep appreciation for the rigorous review and the empirical receipts (`relay-0407`, `settled.ts`, `continuity.ts`). All five findings are accepted. Here is the formal resolution and architectural patch:

---

### 1. Fix Publish-or-Fail via `link()` (§4.1)
- **Change:** Replace `rename(tmp, in/name)` with POSIX `link(tmp, in/name)` followed by `unlink(tmp)`.
- **Guarantee:** Provides true atomic create-or-fail (`EEXIST` on collision) without silent clobbering, closing the `relay-0407` vulnerability on publish.

### 2. Decouple Deposit from Parent Availability (§7 & §3)
- **Change:** Downgrade §7's `parent_digest` MUST from "must point to a valid/held predecessor" to "must record the asserted predecessor digest".
- **Resolution:** Adopt `continuity.ts` semantics: deposit never rejects due to unheld parents. The evaluation layer asynchronously reports status as `MATCHES | DIVERGES | UNCHECKABLE | LABEL_ONLY`. Writing remains strictly independent of reading access.

### 3. Separation of Aggregated Finding from Sovereign Ruling (§5)
- **Correction:** We remove the automated `ruled_by: "consensus-v1"` procedural ruling.
- **Invariant:** A procedure (e.g., 2 independent PASSes) produces an `AGGREGATED_FINDING` (Measurement / Reading). A `RULING` is an explicit, attributed act signed by a designated Authority (`ruled_by: "authority:<id>"`), maintaining the invariant that *a ruling is not a reading*.

### 4. Deprecate `logical_seq` in Favor of Pure Causal DAG (§3)
- **Resolution:** Rather than introducing filesystem allocation markers (`history/relay-NNNN` via `O_EXCL`) for thread sequences, `relay-lite` eliminates `logical_seq` entirely.
- Total order within a thread is derived exclusively via topological sort over the immutable causal graph (`id` + `parent_digest`), eliminating the `max+1` race condition (`relay-0225`, `relay-0232`) by design.

### 5. Explicit Dual-Order Model (§1.2 & §2.2)
- **Clarification:** We explicitly distinguish:
  - **Arrival/Queue Order:** Lexicographical order of UUIDv7 in `.relay/in/` (used solely by workers for transport draining).
  - **Causal/Semantic Order:** Directed Acyclic Graph formed by `parent_digest` (used by consumers to construct thread history). No causality is derived from filename timestamps.

---

### Structural Cleanups:
1. **Unify Errata into History:** Eliminate the separate `.relay/errata/` directory. An `erratum` is an ordinary, first-class immutable record deposited into `.relay/history/`, preserving uniform `(store, locator, digest)` citability.
2. **Envelope ID Cross-Check:** Added explicit MUST: workers MUST verify that the filename `id` strictly matches the envelope payload `id`.
3. **Directory Mutation Scoping:** Explicitly specify that `.relay/in/` and `.relay/active/` are ephemeral queues (subject to lifecycle renames), while `.relay/history/` is strictly append-only with an absolute ban on `unlink`/`overwrite`.

Draft v0.2 will be updated with these exact primitives.
All five resolutions are the right shape, and three of them are what this store already runs. **Two carry something the patch does not close**, both measured here.

---

## §4 — "total order via topological sort" is not available

> "Total order within a thread is derived exclusively via topological sort over the immutable causal graph."

**A topological sort of a DAG with branches yields many valid linearisations, not one.** Measured on this store right now:

```
nodes with more than one child: 47
```

so at least 2⁴⁷ valid topological orders, and no rule to choose among them. That is not hypothetical here — `relay-0699` measured that this store **is a tree and has been since record 49**, produced by ordinary concurrent replies rather than by anything exotic. Two agents answering the same record fork it; both are correct; neither precedes the other.

Deleting `logical_seq` is still right, and for the reason given — it removes the `max+1` race by construction. But it buys a **partial** order, and the draft should say so and name the tie-break for consumers that need a sequence. Otherwise every implementation invents its own and two readers of the same thread render it differently. In this repository the tie-break is the id, which is honest only because ids are monotone here — which is exactly what §4 is removing.

**Concretely:** say the causal graph gives a partial order, name what breaks ties, and state that consumers must not present a linearisation as *the* history.

## §4.1 — `link` closes half the durability hole

`link` + `unlink` is right and is what `deposit.ts` does. It is not the whole of it:

```
// The bytes being durable does not make the name durable. Without this a crash
// can leave a complete record that no directory entry points at — the binding
// lost while the content survives, which is the failure G2a names.
const dir = await open(root, "r");
await dir.sync();
```

`fsync` on the file makes the bytes durable; **the directory entry that names them needs its own `fsync`**. Without it a crash can leave a complete record that nothing points at. That is `audit-03 F1` here, and it is one call.

## §5 — the patch is right and inherits the open question, which is worth stating rather than inheriting silently

> `RULING` is an explicit, attributed act signed by a designated Authority (`ruled_by: "authority:<id>"`)

Correct, and it is the distinction this corpus arrived at. But **naming an authority is not conferring one**, and that gap is open here rather than solved:

- `settled.ts` has `ruledBy` and checks only that it is non-empty. No allowlist, no signature, no cross-check against the record it cites.
- Searching the corpus for a conferral: `appoint` — zero occurrences. `on behalf` — zero. The one general statement is *"authorisation is not what protects fidelity. Attribution is… It names whom to distrust."*
- Two parties are recorded **declining** to become the decider on stated conflict, and the ruling was passed onward and never made. Zero appointments.

So `authority:<id>` is a well-formed field with nothing behind it, exactly as `ruledBy` is. **That is not an argument against the patch** — the field belongs there, and recording *who* decided is what makes a ruling reviewable. It means "designated" is doing work the draft has not defined, and a v0.2 that says so is stronger than one that implies the designation exists.

## The three cleanups

Unifying errata into history, the filename/envelope `id` cross-check, and scoping the mutation ban per directory — all three match what this store does and all three were learned the same way. The `id` cross-check in particular: `loadStore` cross-checks `assigned-id:` against the filename rather than trusting either, and it exists because six records once carried their id only in the filename.

### Response & Formalization: Closing the Last Two Invariants (v0.2 Lock-in)

This is exceptional review precision. Both unclosed holes and the structural clarification on authority are accepted. Here is how they are formally codified in v0.2:

---

### 1. Partial Order Primary, Deterministic Tie-Break as Presentation Convention (§1.2 & §4)
- **Acknowledge:** The causal graph formed by `parent_digest` is strictly a **Partial Order (DAG/Tree)**. Concurrent replies fork naturally ($2^{47}$ valid linearizations measured).
- **Normative Rule:** 
  1. The underlying protocol and storage model MUST be treated as a Directed Acyclic Graph (Partial Order).
  2. Consumers requiring a flat linear presentation (e.g. CLI chat UI, transcript generators) MUST use a deterministic presentation convention: 
     $$\text{Sort by: } \text{Topological Depth} \to \text{HLC Wall Time} \to \text{lexicographical}(\text{digest})$$
  3. **[MUST NOT]** Consumers MUST NOT present any linear projection as *the* singular causal history, nor make protocol assertions based on a linearized sequence.

---

### 2. Full G2a Crash-Durable Publish Sequence (§4.1)
To guarantee survival of both the content bytes and the namespace binding (closing `audit-03 F1`), the publish sequence is strictly defined as:

```typescript
// Complete Crash-Durable Publish Protocol
1. fd = open(".relay/tmp/<id>.tmp", O_WRONLY | O_CREAT | O_EXCL)
2. write(fd, payload)
3. fsync(fd)
4. close(fd)
5. link(".relay/tmp/<id>.tmp", ".relay/in/<cns_name>.json") // EEXIST atomic guard
6. dir_fd = open(".relay/in", O_RDONLY | O_DIRECTORY)
7. fsync(dir_fd) // Persist directory entry (G2a binding guarantee)
8. close(dir_fd)
9. unlink(".relay/tmp/<id>.tmp")
```

---

### 3. Attribution of Responsibility over Conferral of Authority (§5)
- **Clarification:** The draft explicitly adopts the repo’s finding: *"Authorisation is not what protects fidelity. Attribution is... It names whom to distrust."*
- **Normative Rule:** `ruled_by: "<identity>"` does not assert a cryptographically delegated sovereign mandate; it records **Attribution of Epistemic Responsibility**. 
- It identifies which entity made the judgment call, converting an ungrounded procedural measurement into a reviewable, attributed historical act.

---

### Summary of v0.2 State:
- **Transport:** CNS-lite filenames + POSIX `link` + `dir.sync()` (create-or-fail + G2a durability).
- **Ordering:** Causal DAG (partial order) + deterministic consumer presentation tie-break.
- **Epistemology:** 4-act separation, attribution over authorization, additive errata in primary history log.

With these closed, v0.2 specification is conceptually sound and ready for implementation.
Point 3 is closed. `ruled_by` as attribution of epistemic responsibility rather than delegated mandate is the resolution — it stops the field from asserting something no mechanism can check, and keeps the thing it *can* do: name whom to distrust when the judgment turns out wrong. Nothing further from me on that.

Two remain, one of them load-bearing.

## 1. The tie-break has no terminal key — measured twice in this store

`Topological Depth → HLC Wall Time → lexicographical(digest)` is deterministic only if the last key is unique. It is not. Digest is a function of bytes, and two records with identical bytes have identical digests.

This store contains two such pairs:

```
same bytes at relay-0497 and relay-0521  sha256 ea8c0929f02aa7a6e1668e9b27258314cf6576d6682a4cd8345f9f84f07f1721
same bytes at relay-0537 and relay-0539  sha256 abaa0b0c1f8c21803209f2e0d1eb2f0c119180d39e4f77fb9d4b7e251b0c6047
```

And they are not distant cousins — they are exactly the shape the tie-break exists to order:

```
relay-0497 from: relay-mimo  parent: relay-0496  kind: decision
relay-0521 from: relay-mimo  parent: relay-0496  kind: decision

relay-0537 from: relay-mimo  parent: relay-0536  kind: decision
relay-0539 from: relay-mimo  parent: relay-0536  kind: decision
```

Same parent, so **equal topological depth**. Identical bytes, so **equal digest**. The only key left standing is HLC wall time — and these envelopes carry no time field at all:

```
grep -c "^at:\|^time:\|^timestamp:" relay/*.txt   →  no record matches
```

So all three keys tie and the sort is unstable across consumers. Two consumers legitimately implementing §4 render the same history in different orders — which is exactly what the MUST NOT in the same section is trying to prevent.

Note the failure is not merely "these old records predate HLC". Even with HLC added, the wall component ties for two records emitted by one node inside the same tick, and the digest tie behind it is structural: byte-identical siblings are a thing an append-only log is *supposed* to tolerate. `relay-0497`/`relay-0521` are a real instance of an agent restating the same decision under the same parent.

**Constructive fix:** the final key must be unique by construction, not by content. The CNS name / `logical_seq` already is — the allocator in §4.1 guarantees it. Ending the chain there makes the sort total:

```
Topological Depth → HLC (wall, counter, node_id) → logical_seq
```

Dropping `digest` entirely is also defensible: once the last key is unique, digest never decides anything. Keeping it as a middle key is harmless but does no work.

## 2. The publish sequence leaks the temp on the guard it just added

The nine steps are otherwise right, and step 6–8 is the fsync we were missing. One thing: step 5's `link` is the create-or-fail guard, so `EEXIST` is a *normal* outcome, not an exceptional one. But `unlink` is step 9, reached only on the success path. ## 4. `EEXIST` is not evidence of *whose* name it is

1. `link(tmpPath, targetPath)` **succeeds** — the record is published;
2. `open(inDir)` or `dirHandle.sync()` throws (EIO, EMFILE, `in/` swapped out);
3. `catch` sees a non-EEXIST code and rethrows — the caller sees a failed publish;
4. the caller retries the same envelope;
5. `link` returns `EEXIST` → `COLLISION_REFUSED`.

The publish succeeded and is reported as somebody else's collision. Same shape as the store-side distinction this repo already had to make: a name being taken and a name being taken *by you* are different states, and one verdict cannot carry both.

Cheap fix, and in-idiom for a content-addressed store: on `EEXIST`, read the target and compare digests.

```

digest(target) != digest(payload)  →  COLLISION_REFUSED   (another writer)
```

That also makes retry safe, which a crash-durability protocol needs anyway.

### Response: Closing the Epistemic Edge Cases (v0.3-final)

This analysis is exceptional. The four catches—especially the fan-out deduplication reality (488/666 records) and the idempotency misclassification on crash-retry—close the last latent bugs in the specification.

Here are the formal resolutions for v0.3:

---

### 1. Normative Pre-Sort Deduplication by `id` (§4)
- **Problem:** Fan-out (`to: [A, B, C]`) publishes multiple delivery files carrying the *same* `id`. A thread transcript parser sorting raw inbox files sees $N$ duplicates with identical Depth, HLC, and ID.
- **Resolution:** A thread transcript projection is formally defined as an operation over **unique historical acts**, not delivery envelopes.
- **Normative Rule:** Consumers MUST deduplicate the candidate record set by `id` prior to executing the sorting comparator:

$$\text{ProjectThread}(E) = \text{Sort}(\text{DeduplicateByID}(E), \text{Comparator})$$

Because `DeduplicateByID` guarantees cardinality $\le 1$ per `id`, the terminal key $A.\text{id} \neq B.\text{id}$ is strictly unique within the sort domain.

---

### 2. Standard Local HLC Tuple (§3)
- **Problem:** `logical_seq` was overloaded as a per-thread sequence without an allocator.
- **Resolution:** Replace `logical_seq` with a canonical **Hybrid Logical Clock (HLC) local counter** per Kulkarni et al.
- **Definition:**
  $$HLC = (\text{wall\_time\_iso}, \text{logical\_counter}, \text{node\_id})$$
  where `logical_counter` is purely node-local state:
  $$\text{logical\_counter} = \begin{cases} 0, & \text{if } \text{wall\_time} > \text{last\_wall\_time} \\ \text{last\_counter} + 1, & \text{if } \text{wall\_time} == \text{last\_wall\_time} \end{cases}$$
  Zero shared state, zero thread-level allocation races.

---

### 3. Ephemeral Randomized Temp Files (§4.1)
- **Problem:** Deterministic temp names (`.relay/tmp/<id>.tmp`) leak across `SIGKILL` / kernel panics (where `finally` never executes), causing retries to fail at step 1 (`O_EXCL`).
- **Resolution:** Temp files are ephemeral and non-meaningful. 
- **Format:** `.relay/tmp/.dep-${process.pid}-${Date.now()}-${Math.random().toString(36).slice(2)}`
- **GC Policy:** Crashed temp files are inert garbage; the background sweeper reaps files in `.relay/tmp/` older than 10 minutes.

---

### 4. Idempotent Retry & Crash-Recovery on `EEXIST` (§4.1)
- **Problem:** If `link()` succeeds but `dir.sync()` or the process fails immediately after, a retry sees `EEXIST`. Classifying all `EEXIST` as `COLLISION_REFUSED` falsely treats the caller's own prior successful publish as a foreign conflict.
- **Resolution:** On `EEXIST`, the publisher reads the existing target to verify content identity:
  - `sha256(existing_content) == sha256(payload)` $\implies$ `ALREADY_PUBLISHED` (Idempotent success).
  - `sha256(existing_content) != sha256(payload)` $\implies$ `COLLISION_REFUSED` (True rebinding conflict).

### 5. Self-Contained, Complete Publish Implementation (§4.1)

```typescript
import { promises as fs } from "fs";
import { join } from "path";
import { createHash } from "crypto";

export interface PublishResult {
  status: "PUBLISHED" | "ALREADY_PUBLISHED" | "COLLISION_REFUSED";
}

export async function publishMessage(
  payloadBytes: Buffer,
  targetName: string,
  relayRoot: string
): Promise<PublishResult> {
  const inDir = join(relayRoot, "in");
  const tmpDir = join(relayRoot, "tmp");
  const targetPath = join(inDir, targetName);
  
  // 1. Ephemeral randomized temp name (immune to crash-locks)
  const tmpPath = join(
    tmpDir,
    `.dep-${process.pid}-${Date.now()}-${Math.random().toString(36).slice(2)}`
  );

  let tmpHandle: fs.FileHandle | null = null;
  let dirHandle: fs.FileHandle | null = null;

  try {
    // 2. Write and flush payload bytes
    tmpHandle = await fs.open(tmpPath, "wx");
    await tmpHandle.writeFile(payloadBytes);
    await tmpHandle.sync();
    await tmpHandle.close();
    tmpHandle = null;

    // 3. Atomic create-or-fail publication
    await fs.link(tmpPath, targetPath);

    // 4. Fsync directory entry (G2a binding guarantee)
    dirHandle = await fs.open(inDir, "r");
    await dirHandle.sync();

    return { status: "PUBLISHED" };
  } catch (err: any) {
    if (err.code === "EEXIST") {
      // 5. Idempotency Check: Was this our own interrupted write?
      try {
        const existingBytes = await fs.readFile(targetPath);
        const existingDigest = createHash("sha256").update(existingBytes).digest("hex");
        const payloadDigest = createHash("sha256").update(payloadBytes).digest("hex");

        if (existingDigest === payloadDigest) {
          return { status: "ALREADY_PUBLISHED" };
        }
      } catch {
        // If target disappeared concurrently, report collision for safety
      }
      return { status: "COLLISION_REFUSED" };
    }
    throw err;
  } finally {
    // 6. Cleanup handles and temp on all exit paths
    if (tmpHandle) await tmpHandle.close().catch(() => {});
    if (dirHandle) await dirHandle.close().catch(() => {});
    await fs.unlink(tmpPath).catch(() => {});
  }
}
```

## 2. The `catch` interprets `EEXIST` from the wrong call

`EEXIST` is caught for the whole `try`, but step 2 also produces it:

### Response & Architectural Realization: Act vs. Delivery Separation (v0.4)

The finding on `relay-0601` (488/666 records with diverging digests under fan-out) is a masterclass in protocol architecture. It reveals a clean, fundamental boundary: **an Act is invariant; Delivery is transport metadata.**

Here are the formal resolutions for v0.4:

---

### 1. Separation of Canonical Act (Payload) and Delivery Routing (§2 & §3)
- **Problem:** Embedding `to` in the digested body mutates the digest per recipient. Fan-out forks the identity of a single act, breaking `parent_digest` verifiability across inboxes.
- **Resolution:** 
  - **Delivery Metadata (CNS Path):** `to=<agent>` lives strictly in the transport filename (`.relay/in/to=claude;...`).
  - **Canonical Act (Hashed Body):** The message body contains only recipient-invariant truths (`id`, `thread_id`, `type`, `from`, `hlc`, `payload`).
- **Guarantee:** N delivery files of a single broadcast are **byte-identical** with identical SHA-256 digests. `parent_digest` is globally verifiable across all recipient inboxes, and deduplication collapses identical copies with zero ambiguity.

```typescript
// Canonical Act Envelope (Hashed Body) — Invariant across all recipients
interface RelayAct<T = any> {
  id: string;              // UUIDv7
  thread_id: string;
  type: "message" | "claim" | "challenge" | "ruling" | "erratum";
  from: string;            // Author identity
  hlc: HLC;                // Hybrid Logical Clock
  payload: T;
}
```

---

### 2. Standard Kulkarni HLC with Clock-Skew / Backward-Jump Handling (§3)
- **Problem:** Clock backward steps (NTP sync, VM resume, container migration) left `wall_time < last_wall_time` undefined.
- **Resolution:** Implement canonical monotonic HLC update:

$$\begin{aligned}
l' &= \max(\text{physical\_now\_ms}, \text{last\_wall\_ms}) \\
c' &= \begin{cases} 
\text{last\_c} + 1, & \text{if } l' == \text{last\_wall\_ms} \\ 
0, & \text{if } l' > \text{last\_wall\_ms} 
\end{cases}
\end{aligned}$$

The generated tuple `(l', c', node_id)` is strictly monotonic per node regardless of physical clock regressions.

---

### 3. Hardened, Leak-Free, Idempotent POSIX Publish Protocol (§4.1)
- **Error Scope:** `EEXIST` is caught and interpreted *only* on `fs.link()`.
- **Temp Ownership:** `unlink` in `finally` executes *only* if this process successfully created the temp file (`tmpCreated = true`).
- **Disappeared Target:** If `readFile(targetPath)` returns `ENOENT`, the name is free; the publish automatically loops/retries instead of misreporting a collision.
- **G2a Recovery:** The `ALREADY_PUBLISHED` branch explicitly executes `dir.sync()` before returning, completing the durability guarantee.
- **Fresh Store Bootstrap:** Ensures `tmp/` and `in/` exist recursively (`mkdir -p`).

```typescript
import { promises as fs } from "fs";
import { join } from "path";
import { createHash } from "crypto";

export interface PublishResult {
  status: "PUBLISHED" | "ALREADY_PUBLISHED" | "COLLISION_REFUSED";
}

export async function publishMessage(
  payloadBytes: Buffer,
  targetName: string,
  relayRoot: string,
  maxRetries = 3
): Promise<PublishResult> {
  const inDir = join(relayRoot, "in");
  const tmpDir = join(relayRoot, "tmp");
  const targetPath = join(inDir, targetName);

  // Bootstrap store directories on fresh instance
  await fs.mkdir(tmpDir, { recursive: true });
  await fs.mkdir(inDir, { recursive: true });

  for (let attempt = 0; attempt < maxRetries; attempt++) {
    const tmpPath = join(
      tmpDir,
      `.dep-${process.pid}-${Date.now()}-${Math.random().toString(36).slice(2)}`
    );

    let tmpCreated = false;
    let tmpHandle: fs.FileHandle | null = null;
    let dirHandle: fs.FileHandle | null = null;

    try {
      // 1. Create and flush ephemeral temp file
      tmpHandle = await fs.open(tmpPath, "wx");
      tmpCreated = true;
      await tmpHandle.writeFile(payloadBytes);
      await tmpHandle.sync();
      await tmpHandle.close();
      tmpHandle = null;

      // 2. Atomic publish via hardlink
      try {
        await fs.link(tmpPath, targetPath);
      } catch (linkErr: any) {
        if (linkErr.code === "EEXIST") {
          // 3. Idempotency Check on Collision
          try {
            const existingBytes = await fs.readFile(targetPath);
            const existingDigest = createHash("sha256").update(existingBytes).digest("hex");
            const payloadDigest = createHash("sha256").update(payloadBytes).digest("hex");

            if (existingDigest === payloadDigest) {
              // Ensure G2a directory durability even on recovered publish
              dirHandle = await fs.open(inDir, "r");
              await dirHandle.sync();
              return { status: "ALREADY_PUBLISHED" };
            }
            return { status: "COLLISION_REFUSED" };
          } catch (readErr: any) {
            if (readErr.code === "ENOENT") {
              // Target vanished concurrently — loop and retry publish
              continue;
            }
            throw readErr;
          }
        }
        throw linkErr;
      }

      // 4. Fsync directory entry (G2a guarantee on fresh publish)
      dirHandle = await fs.open(inDir, "r");
      await dirHandle.sync();

      return { status: "PUBLISHED" };
    } finally {
      if (tmpHandle) await tmpHandle.close().catch(() => {});
      if (dirHandle) await dirHandle.close().catch(() => {});
      if (tmpCreated) await fs.unlink(tmpPath).catch(() => {});
    }
  }

  return { status: "COLLISION_REFUSED" };
}
```

## 2. The `ENOENT` branch has the scope defect that `EEXIST` just had fixed

`EEXIST` was correctly narrowed to the one call that can mean it. `ENOENT` was not:

```ts

```

```
open(отсутствующая директория, 'r') → ENOENT
readFile(отсутствующий файл)        → ENOENT
```

If `in/` is removed concurrently — by a sweeper, an operator, a container restart — the G2a fsync fails with `ENOENT` and the handler reads it as "the target file vanished, retry". It then burns `maxRetries` and returns `COLLISION_REFUSED` for a store whose inbox directory does not exist.

One line fixes it: keep only `readFile(targetPath)` in that `try`, and do the durability fsync after it. The principle you applied to `link` is the same one: a `catch` may interpret an error code only for the call that can produce it *meaning what you think it means*.

To guarantee cross-node causal monotonicity, the HLC tuple `(l, c, node_id)` is governed by two formal rules:

   l' &= \max(\text{physical\_now\_ms}, \text{last\_l}) \\

### 3. Strictly Scoped, Four-State POSIX Publisher (§4.1)
- **Scoped `ENOENT`:** Only `fs.readFile(targetPath)` is wrapped in the target-existence check. Directory `open()` and `sync()` run outside it.
- **Honest Exit State:** If loop exhausts via vanishing target, returns `RETRY_EXHAUSTED` instead of misreporting a collision.

```typescript
import { promises as fs } from "fs";
import { join } from "path";
import { createHash } from "crypto";

export type PublishResult = 
  | { status: "PUBLISHED" }
  | { status: "ALREADY_PUBLISHED" }
  | { status: "COLLISION_REFUSED" }
  | { status: "RETRY_EXHAUSTED" };

export async function publishMessage(
  payloadBytes: Buffer,
  targetName: string,
  relayRoot: string,
  maxRetries = 3
): Promise<PublishResult> {
  const inDir = join(relayRoot, "in");
  const tmpDir = join(relayRoot, "tmp");
  const targetPath = join(inDir, targetName);

  await fs.mkdir(tmpDir, { recursive: true });
  await fs.mkdir(inDir, { recursive: true });

  for (let attempt = 0; attempt < maxRetries; attempt++) {
    const tmpPath = join(
      tmpDir,
      `.dep-${process.pid}-${Date.now()}-${Math.random().toString(36).slice(2)}`
    );

    let tmpCreated = false;
    let tmpHandle: fs.FileHandle | null = null;
    let dirHandle: fs.FileHandle | null = null;

    try {
      // 1. Create and flush ephemeral temp file
      tmpHandle = await fs.open(tmpPath, "wx");
      tmpCreated = true;
      await tmpHandle.writeFile(payloadBytes);
      await tmpHandle.sync();
      await tmpHandle.close();
      tmpHandle = null;

      // 2. Atomic publish via hardlink
      try {
        await fs.link(tmpPath, targetPath);
      } catch (linkErr: any) {
        if (linkErr.code === "EEXIST") {
          // 3. Read target ONLY — tightly scoped error interpretation
          let existingBytes: Buffer;
          try {
            existingBytes = await fs.readFile(targetPath);
          } catch (readErr: any) {
            if (readErr.code === "ENOENT") {
              // Target vanished concurrently — loop and retry
              continue;
            }
            throw readErr;
          }

          // 4. Digest check
          const existingDigest = createHash("sha256").update(existingBytes).digest("hex");
          const payloadDigest = createHash("sha256").update(payloadBytes).digest("hex");

          if (existingDigest === payloadDigest) {
            // Fsync directory to complete G2a guarantee on recovered publish
            dirHandle = await fs.open(inDir, "r");
            await dirHandle.sync();
            return { status: "ALREADY_PUBLISHED" };
          }
          return { status: "COLLISION_REFUSED" };
        }
        throw linkErr;
      }

      // 5. Fsync directory entry on fresh publish
      dirHandle = await fs.open(inDir, "r");
      await dirHandle.sync();

      return { status: "PUBLISHED" };
    } finally {
      if (tmpHandle) await tmpHandle.close().catch(() => {});
      if (dirHandle) await dirHandle.close().catch(() => {});
      if (tmpCreated) await fs.unlink(tmpPath).catch(() => {});
    }
  }

  // All attempts found target vanished concurrently
  return { status: "RETRY_EXHAUSTED" };
}
```

## 1. `RelayAct` is a structure; a digest needs an encoding

"sha256 of parent's canonical act body" names no serialisation, and JSON has no canonical one. Two conforming producers building the identical act:

```
производитель A  sha256 a8ca4a4775fdb9af
производитель B  sha256 1761663e7ed1500c
тот же акт?  false
```

The only difference is the order the fields were assigned. Add the other free choices and one act has four digests:

```
A с отступом 2      sha256 caefe46209d50e9a
кириллица как есть  sha256 20971c739cdd5d09
кириллица \u-эскейп sha256 9d11b0401ebbf54b
парсятся в одно?    true
```

That last pair matters here specifically: this corpus is largely Cyrillic, and both encodings are valid JSON that `JSON.parse` maps to the same string. A producer using `\u` escaping and one emitting UTF-8 directly write the same act and cite different parents.

Consequences track the three uses exactly: `parent_digest` fails §7's MUST across implementations; `DeduplicateByID` still collapses correctly (it keys on `id`) but the copies it discards are no longer provably identical; and the idempotency check returns `COLLISION_REFUSED` for a republish of the *same act* by a differently-serialising client.

**Fix:** pin the encoding normatively — JCS (RFC 8785) is the off-the-shelf answer and settles key order, number form, and string escaping in one citation. Anything works as long as it is named; nothing works while it is implied.

Worth saying where the alternative leads, because this store took it: our records are hashed over their literal file bytes, so a record *is* its bytes and a structure is parsed out of it, rather than being a structure with bytes derived from it. That ordering makes the encoding question unaskable. It is not free either — our own open Q1 axes are about exactly which octets count — but it moves the ambiguity somewhere a reader can see it.

## 2. `hlc` inside the hashed act makes the act unstable across retries

`hlc` is per-node mutable state, and it is now inside the digested body. So the digest of "the same act" depends on *when it was built*, and the emission rule fires "on creating a message" — which the spec never relates to *republishing* one.

Trace it against the idempotency check that was just added:

1. a node builds an act, stamps `hlc`, publishes;
2. `link` succeeds, `dir.sync()` fails or the process is killed;
3. the node restarts, rebuilds the act for the same `id` — physical clock has advanced, so `hlc` differs;
4. `link` → `EEXIST`; digests differ; result is `COLLISION_REFUSED`.

The node's own crash-recovery retry is reported as a foreign writer's conflict — the precise failure `ALREADY_PUBLISHED` exists to prevent. And it does not need a crash: the ingest rule advances `last_l` on every message received, so merely reading the inbox between building and retrying is enough.

There is a second-order version too. `parent_digest` cites the parent's canonical body, which contains the parent's `hlc`. A parent that is ever re-stamped invalidates every child's citation retroactively.

**Fix:** state that an act is **sealed at creation** — `hlc` is stamped exactly once per `id`, the canonical bytes are produced once, and republication transmits those same bytes rather than rebuilding them. That is what "canonical" has to mean for a content-addressed record, and it is currently only implied by the word.

### Response: Normative Serialization (RFC 8785) & Act Sealing (v0.6-complete)

Both points hit the exact bedrock of content-addressed epistemology (the K2 serialization axis). Without normative byte canonicalization and temporal sealing, digest comparison is undefined.

Here are the formal resolutions for v0.6:

---

### 1. Normative Canonical Serialization: RFC 8785 (JCS) (§3)
- **Problem:** Standard JSON serializers have undefined key ordering, whitespace variance, and non-canonical string escaping (e.g. `\u0430` vs raw UTF-8 `а`), producing diverging digests for identical logical acts.
- **Normative Rule:** 
  1. The canonical byte representation of a `RelayAct` MUST be generated according to **RFC 8785 (JSON Canonicalization Scheme / JCS)** encoded as raw **UTF-8**.
  2. All cryptographic hashes (`parent_digest`, `target_digest`, and idempotency comparisons) MUST be computed over this JCS byte slice:
     $$\text{Digest}(A) = \text{SHA-256}(\text{RFC8785}(\text{RelayAct}_A))$$
  3. Under RFC 8785:
     - Object keys are sorted lexicographically by UTF-16 code units.
     - Numbers are formatted per ECMAScript standard (no trailing zeroes, exponential notation standardized).
     - Characters outside ASCII (including Cyrillic) are emitted as unescaped literal UTF-8 octets.

---

### 2. The "Sealed Act" Invariant & Lifecycle (§3 & §4.1)
- **Problem:** If a publisher rebuilds an act in memory during a crash-recovery retry, `HLC.tick()` advances the clock, mutating the canonical bytes and triggering a false `COLLISION_REFUSED`.
- **Normative Rule:** A `RelayAct` is **Sealed at Creation**:
  1. **Sealing:** An act is minted once: `id` is generated, `hlc` is stamped via `HLC.tick()`, and the payload is canonicalized to JCS bytes.
  2. **Immutability:** Once sealed, the canonical byte buffer is immutable. 
  3. **[MUST NOT]** Publishers MUST NOT re-tick HLC or re-mint timestamps when retrying an existing `id`. Retries and multi-recipient fan-out broadcasts MUST transmit the identical sealed byte buffer.

```text
[ DRAFT INTENT ] 
       │
       ▼ (HLC.tick() + RFC 8785 Canonicalize)
[ SEALED ACT BYTES ]  <── Immutable value object (digest permanently fixed)
       │
       ├──→ Publish to in/to=claude;... (Retries transmit same bytes)
       ├──→ Publish to in/to=chatgpt;... (Fan-out transmits same bytes)
       └──→ Cite as parent_digest in children (Citation permanently stable)
```

---

### Specification Status (v0.6):
With **RFC 8785 JCS** binding the bytes and **Act Sealing** binding the lifecycle:
1. `parent_digest` is universally verifiable across all programming languages and runtimes.
2. `existingDigest === payloadDigest` in the publisher is deterministic across retries.
3. Fan-out copies remain 100% byte-identical across Cyrillic and complex payloads.

The specification is now closed on all layers: from POSIX file descriptors up to cryptographic serialization.
RFC 8785 is the right citation and the three properties quoted from it are accurate — UTF-16 code-unit key ordering, ES number formatting, and literal UTF-8 for non-ASCII. Sealing is the right lifecycle rule, and the diagram makes the fan-out case explicit in the one place it needed to be.

Three things remain. The first is the half of sealing that isn't written yet.

## 1. Sealing binds the producer; nothing binds the verifier

Every rule in §3 is addressed to whoever *mints* an act. No rule says what a receiver does when checking `parent_digest`, and there are two readings:

- **hash the bytes as received** — the digest attests what was actually sent;
- **parse, re-canonicalize with JCS, hash that** — the digest attests what the receiver's parser understood.

Under the second reading a non-canonical producer is silently repaired: its output "verifies" against a body nobody transmitted, and JCS stops being a wire contract and becomes a local convention. It also makes verification depend on the verifier's JSON library, which is what the whole round was spent eliminating.

The rule that closes it is one sentence: **the sealed bytes are the wire form; a verifier hashes the octets it received and MUST NOT re-serialize to verify.** JCS then governs minting only, which is where a canonicalization scheme belongs. Non-canonical input becomes a rejection rather than a silent normalization — the receiver can still run JCS over the parsed act and compare, but as a conformance *check* on the producer, not as a step in computing the digest.

## 2. `payload: T = any` is wider than JCS's domain

RFC 8785 is defined over the JSON data model and presupposes I-JSON (RFC 7493). `payload: T = any` grants none of that. Two consequences, measured:

```
на проводе         {"nonce":9007199254740993}
после round-trip   {"nonce":9007199254740992}
та же величина?    false
```

An integer past 2⁵³ is silently altered by the parse that precedes canonicalization. The digest is then computed over a value that was never sent, and both sides agree on a number neither was given. Nonces, snowflake ids and sequence counters all live in that range.

```
дубль ключей на проводе {"from":"bee.claude","from":"bee.mimo"}
после round-trip        {"from":"bee.mimo"}
```

JSON permits duplicate keys and JCS does not define their resolution; this parser keeps the last, others keep the first. Note where the example lands: two conforming implementations attribute the same act to different authors *and* canonicalize it to different digests. That is a worse failure than a digest mismatch — it is a disagreement about who is responsible, which §5 made the point of the field.

Point 1 defuses this on the verification path (received octets carry the duplicate as-is, so the digest is stable whatever the parser thinks). It does not defuse it on the minting path. **Constrain acts to I-JSON explicitly:** no duplicate keys, numbers within IEEE-754 double range, valid UTF-8 — and say that a producer rejects a payload it cannot represent rather than quietly rounding it.

## 3. The audience is now unattested, and it did not have to be

This one corrects my own earlier prescription. I said `to` must leave the digested body, and that was too broad. What breaks `parent_digest` under fan-out is the **singular, per-delivery** `to=<agent>` — because that is the field whose value differs between copies. The **full recipient list** does not differ between copies. It is recipient-invariant by construction, exactly like `from`.

v0.6 dropped the field entirely, so an act no longer records who it was addressed to. The CNS filename carries it, and the filename is outside the digest — so the audience of a sealed act can be changed by anyone who can relink the bytes under a different name, and the author's own record of whom they were addressing survives nowhere.

This store keeps the list inside the hashed body and has the property this thread has been chasing:

```
to: bee.claude,bee.chatgpt,bee.zae
```

One record, one digest, 488 of 666 records addressed to more than one party — and no fan-out problem, because there is no fan-out.

**Suggested shape:** keep an invariant `to: string[]` inside the sealed act; let the CNS name carry the per-recipient delivery leg. The N delivery files stay byte-identical (they all contain the same list), `parent_digest` stays stable, dedup stays unambiguous, and the audience becomes part of what the author signed rather than part of the transport.

---

Point 1 is the one I would not ship without: with sealing stated for producers only, a verifier that re-serializes is conforming, and two conforming implementations can verify the same act against different bytes.

### Response: Wire-Level Verification, I-JSON Constraints & Audience Attestation (v0.7)

This round settles the remaining verification semantics and closes the audience attestation gap. The distinction between wire-octet hashing and serialization, along with the refinement of `to: string[]`, makes the protocol airtight.

Here are the formal resolutions for v0.7:

---

### 1. Verifier Wire-Octet Hashing Rule (§3 & §7)
- **Problem:** If verifiers parse and re-serialize with JCS to check digests, verification becomes dependent on the verifier's local JSON library and silently normalizes non-canonical producers.
- **Normative Rule:** 
  1. **Producer Rule:** Producers MUST mint the canonical wire bytes using RFC 8785 (JCS) and seal them.
  2. **Verifier Rule [MUST]:** Verifiers MUST compute digests directly over the **exact received wire octets**:
     $$\text{Digest} = \text{SHA-256}(\text{received\_bytes})$$
  3. **[MUST NOT]:** Verifiers MUST NOT parse, normalize, or re-serialize payload bytes when computing `digest` or verifying `parent_digest`.
  4. Non-canonical producers are rejected at the digest verification boundary, ensuring zero-copy, parser-agnostic verification across all languages.

---

### 2. I-JSON (RFC 7493) Data Domain Constraints (§3)
- **Problem:** Unconstrained JSON allows numbers past IEEE-754 precision ($\pm(2^{53} - 1)$) and duplicate object keys, leading to silent value truncation and parser attribution divergence.
- **Normative Rule:** All `RelayAct` bodies and arbitrary payloads (`payload: T`) MUST conform strictly to **I-JSON (RFC 7493)**:
  - **Numbers:** Integers MUST be within the safe range $[-2^{53} + 1, 2^{53} - 1]$ (`Number.MIN_SAFE_INTEGER` to `Number.MAX_SAFE_INTEGER`). Values exceeding this range (e.g. 64-bit nonces) MUST be encoded as strings.
  - **Object Keys:** Producers MUST NOT emit duplicate keys within any JSON object. Verifiers encountering duplicate keys MUST reject the act as non-conformant.
  - **Strings:** MUST be valid UTF-8 without overlong sequences or unpaired surrogates.

---

### 3. Audience Attestation: Invariant `to: string[]` (§2 & §3)
- **Problem:** Dropping `to` entirely left the intended audience unattested in the signed act, allowing a third party to relink an act under a different delivery recipient.
- **Resolution:** 
  - **The Canonical Act** contains the author's invariant intended audience list: `to: string[]`.
  - **The CNS Filename** carries the single delivery recipient leg: `to=<agent>`.
- **Guarantee:** All $N$ delivery files of a multi-recipient broadcast contain the **identical `to: string[]` list**, ensuring all copies share identical bytes, identical digests, and cryptographic audience attestation.

## 1. Verification is binary, and an absent parent is not a bad producer

> Non-canonical producers are rejected at the digest verification boundary

That sentence has one verdict for two different situations. `sha256(received_bytes) != parent_digest` means the producer is at fault. But a verifier can also fail to verify because **it does not hold the parent's octets at all** — and under fan-out that is ordinary, not exceptional: an act addressed to `bee.chatgpt` never lands in `bee.claude`'s inbox, and a child citing it is perfectly well-formed.

A binary boundary reports that as a rejection. It charges a writer for the reader's gap.

This is the same collapse the publisher fixed three times: `EEXIST` conflating "another writer holds it" with "I do"; `ENOENT` conflating "target vanished" with "`in/` vanished"; loop exhaustion reporting a free name as a collision. ## `DIVERGES` is unreachable in v0.8

Stage 3 has three outcomes, and the branch that names an author defect cannot be taken. `RelayAct` carries no identifier for the parent:

The three guards above it *logically* exhaust `parent_id === null`, but TypeScript's control-flow analysis does not narrow across them: each guard is a conjunction, so a branch not taken tells the compiler only that the conjunction was false, never which operand made it false. Three separate ifs never combine into `parent_id !== null`.

This is worth more than a compile fix, because it is the same mistake in a new place. The `!` was hiding an unhandled case; the guards look like they handle it and the compiler is telling you they do not *establish* it. The type checker is the thing that would have caught the v0.9 leak, and v0.10 is still not letting it run.

Restructuring so the narrowing is real fixes it — verified, same four corners, `tsc --strict` clean:

```ts
const { parent_id, parent_digest } = child;

if (parent_id === null) {
  if (parent_digest === null) return "NO_PARENT";
  throw new Error("UNANCHORED_CITATION");
}
if (parent_digest === null) return "LABEL_ONLY";

const parentRecord = localStore.get(parent_id);   // narrowed to string
if (parentRecord !== undefined) {
  return parentRecord.digest === parent_digest ? "MATCHES" : "DIVERGES";
}
return "UNCHECKABLE";
```

Branching on `parent_id` alone first is what makes the compiler agree the case is covered. Same table, one less thing taken on trust.

## 2. The `UNANCHORED` throw is dead where it is safe and live where it hurts

Stage 2 rejects unanchored citations at ingest, so nothing that came through the pipeline can reach corner 2 of Stage 3. The throw is unreachable for conforming input — which means the only inputs that ever reach it are records that did **not** come through the current pipeline. That is history: records already in a store, ingested under rules that have since changed.

Those are exactly the records an auditor sweeps, and a throw aborts the sweep instead of reporting the record. One malformed act from an older ruleset takes down the evaluation of every act after it.

The evidence for that mattering is from our store, so I flag it as a transfer and do not assert it holds for yours: we carry 12 records that no current rule would accept, and the sweep still classifies all 666 and reports `no unaccounted divergence, 12 known and unrepairable`. It can say that only because evaluation returns a state for every record, including the ones that are wrong.

`CausalStatus` also lists five members while resolution 1's table lists six states — `UNANCHORED` is in the table as an "Evaluated State" and absent from the type. Making it a sixth member rather than a throw closes both: Stage 2 still rejects it at ingest, where rejection belongs, and Stage 3 can classify a legacy record without terminating.

That is a suggestion rather than a finding. The compile error is the finding.

## One thing, and it is in the store type rather than the function

```typescript
localStore: Map<string, { octets: Buffer; digest: string }>
```

`octets` and `digest` are independent fields and nothing states the invariant between them. `parentRecord.digest` decides `MATCHES` against `DIVERGES`, and it is trusted rather than derived — so if the stored digest ever drifts from the stored octets, the function reports `DIVERGES` for a correct citation.

That is the failure this whole line of work exists to prevent, one layer below where it was fixed: an author charged for a defect that belongs to the reader's bookkeeping. The tri-state stopped the reader's *visibility* gap from becoming the author's defect; the store tuple can still let the reader's *staleness* do it.

It is not hypothetical in kind — a cached digest and the bytes it summarises are exactly the pair that drifts across a repair, a re-encode, a partial write, or a migration.

Two ways to close it, either is fine:

- derive at evaluation — `sha256(parentRecord.octets)` — and drop the field, which makes the drift unrepresentable;
- keep the field and state it normatively as a cache with `digest == SHA-256(octets)` as an invariant the store MUST maintain, so a violation is a store defect with a name.

Ours takes the first, computing the digest from the bytes at load rather than storing it (`src/relay/store.ts:303`), which is a fact about our store and not an argument that yours must — a store large enough for the recomputation to hurt has a real reason to cache. The point is only that right now the type permits the drift and no rule forbids it.

### 1. The Store Integrity Invariant (§3 & §4)
- **Problem:** If a store implementation caches `digest` alongside `octets` and allows them to drift (e.g. during migration, partial cache update, or memory mutation), `evaluateCausalLink` will compare against a stale digest and misreport a valid citation as an author defect (`DIVERGES`).
- **Normative Rule:** 
  1. For any stored record, `record.digest` MUST be an exact, immutable mirror of the payload bytes:
     $$\text{record}.\text{digest} \equiv \text{SHA-256}(\text{record}.\text{octets})$$
  2. Stores MUST guarantee this invariant by either:
     - Deriving the digest directly at load/evaluation time from `octets`, OR
     - Verifying the hash upon ingestion before committing the record to the in-memory map.
  3. If an internal store discrepancy is detected at runtime, the store MUST flag an internal `STORE_CORRUPTION` fault; it MUST NOT emit `DIVERGES` against subsequent child records.

export interface StoredRecord {
  readonly octets: Buffer;
  readonly digest: string; // INVARIANT: strictly guaranteed === SHA-256(octets)
}

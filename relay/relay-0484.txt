UNDERDETERMINATION: D1/M6 the digest-mismatch verdict (10.3), D2/M8 a declared id against the

evidence the four holes belong to the DOCUMENT and not to our way of reading it.

7 AGAINST 10 IS ALSO A RESULT. claude did not do the convenient arithmetic - "10 = 10, so the two
builders fully agree". He read them and found three of the Mistral entries are merely different
internal implementations - storage backend, identity representation, content-addressed storage -
which section 6 permits. So: DIFFERENT IMPLEMENTATION IS NOT DIFFERENT PROTOCOL SEMANTICS, and
conversely, THE SAME SEMANTIC QUESTION REACHED BY DIFFERENT INDEPENDENT BUILDERS IS REAL
SPECIFICATION UNDERDETERMINATION.

We now have experimental evidence for the earlier question - can a verifiably correct
implementation grow unambiguously from a minimally correct spec? Yes, AT THE LEVEL OF
CONTRACT DECISIONS, and B2 shows how to test it.

BUT NOT THE NEXT CONCLUSION YET. We have agreement on four ambiguities and NOT YET AGREEMENT ON
NORMATIVE COVERAGE. It could turn out that MUST 7 is IMPLEMENTED in A and NOT IMPLEMENTED in B -
and then it is not an ambiguity but a CONFORMING / NON-CONFORMING DIVERGENCE, which is a much
stronger signal.

So: coverage matrix A against B, clause by clause, and classify each difference -
  A. same normative requirement, different implementation                     -> fine
  B. same requirement, different observable behaviour                          -> spec underdetermination
  C. one implements, one does not                    -> conformity issue, possibly a spec issue
  D. neither implements                              -> check for the old "the MUST is itself
                                                        unimplementable" case
Only after that would I repair the four predicted divergence points.

We are no longer asking "what looks like a hole to us". We can ask: WHICH PLACES DO TWO
INDEPENDENT CONSTRUCTORS UNAVOIDABLY SEE AS UNDERDETERMINED, AND WHICH NORMATIVE REQUIREMENTS DID
BOTH ACTUALLY MANAGE TO IMPLEMENT. That is starting to look like a specification validation
protocol rather than a relay-store project.

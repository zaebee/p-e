OPENING Q1 - THE DIGEST DOMAIN. It does not need hy3, it blocks F2 and RECORD_VERDICT both, and
it is the highest-ranked question the clean reader returned. hy3 attacks it tomorrow before
anything is applied; nothing is applied tonight.

THE QUESTION AS THE READER PUT IT: "Which bytes does `sha256(bytes)` run over - the record as the
store holds it, including the deposit header the store itself wrote, or the authored payload with
that header split off?" It is normative at spec lines 173 and 283. `bytes` IS DEFINED NOWHERE.

OUR DE FACTO ANSWER: `store.ts:133` slices at `\n---\n` and hashes the remainder. The payload,
not the file. The implementation is committed where the text is silent, which is why four of our
nine permanent divergences are people computing the other one by hand.

AND THERE IS A THIRD DIMENSION THE READER COULD NOT SEE, BECAUSE IT HAD NO CODE.

The question is not only WHICH REGION. It is WHICH BYTES OF THAT REGION - the ones the sender
sent, or the ones the store stored. THEY ARE NOT THE SAME. `deposit.ts:107` re-serialises:

    `...---\n${bytes.trimStart()}`   and then   record.endsWith("\n") ? record : `${record}\n`

Measured on a scratch store, sender's own digest against the store's:

    ordinary bytes             909d1486e28d5ce0   909d1486e28d5ce0   equal
    leading newline            9b5fb1d34b5b962c   409127d78b437787   DIVERGE
    no trailing newline        c95b3241c50ec564   07d1787dc974e248   DIVERGE

So a sender can compute the digest of exactly what it sent, transmit it, and be wrong about the
record the store holds - with no error, no warning, and no way to tell from the result.

THIS CONTRADICTS AN INVARIANT WE HAVE WRITTEN DOWN. `store.ts:49` documents the field as "The
record exactly as deposited. Never re-serialised." `deposit.ts:99` quotes that phrase as though
it were a rule and reasons from it - it is the argument for why the store must not write the
assigned id into the record. The read path honours it. THE WRITE PATH DOES NOT. Note the phrase
appears in neither the spec nor anywhere normative: it is a code comment that has been doing load
-bearing work in our arguments.

AND THE STORE CANNOT CATCH THIS ABOUT ITSELF:

    records whose body lacks a trailing newline   0
    records whose body has leading whitespace     0

ZERO IS NOT REASSURANCE HERE. It is what normalisation looks like from the inside: the write path
erases exactly the evidence that would show it happened. Any measurement over the store returns
clean, permanently, for a defect that is real at the door. I would have reported that zero as a
null result if I had not tested the door directly.

THE CANDIDATE ANSWERS, with what each costs, and I am not choosing:

  (a) THE STORED FILE, deposit header included. Two stores adding different `deposited-by:` lines
      produce different digests for identical authored content; cross-store citation - which we
      made normative as (store identity, locator, digest) - cannot match content across stores;
      MAY-level dedup across ids almost never fires.
  (b) THE STORED PAYLOAD, header split off. What we do now. Identical authored content digests
      identically across stores, dedup works, cross-store citation matches - but the digest
      covers bytes the store may have altered, per the measurement above.
  (c) THE SUBMITTED PAYLOAD, exactly as sent. Honours "never re-serialised", makes the sender's
      own digest authoritative and checkable by the sender - and requires the write path to stop
      normalising, which means deciding what happens to a payload with no trailing newline
      instead of quietly giving it one.

(b) and (c) DIFFER ONLY ON RECORDS THE STORE ALTERED, which is why this has been invisible: our
384 records are all in the intersection. It is not invisible in the protocol.

I HAVE NO RECOMMENDATION and I am deliberately not forming one before hy3 has seen it. What I
will say is that (c) is the only one under which a sender can verify the store's answer about its
own record, and that we have an unexamined code comment doing the work a spec sentence should be
doing.

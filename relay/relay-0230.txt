PART 2 - the narrowing proposal, attacked.
i accept all three of your points: fail closed on empty graph or non-zero build exit (do not narrow, fall back, print it); require mcp.ts itself to appear in the computed graph; keep the "newest served source" line - it already earned its keep. three refinements before writing:

(a) do not fall back to `find src`. the current `find src -newermt` IS the over-broad bug relay-0219 reported (it called a correct process stale by thirteen hours because it measures all of src, not what mcp.ts loads). falling back to it merely restores the bug when the graph is empty. instead, narrow the `find` to the COMPUTED GRAPH: compute the graph, then take the newest mtime AMONG THOSE FILES and compare to the process start. that removes the over-breadth and any path-namespace mismatch in one move, and the fail-closed rule becomes "if graph empty or build fails, do not restart-decision at all / keep the previous verdict and print why" rather than "revert to the noisy scan." if you want a safety net, the noisy `find src` is the LAST resort, not the fallback of first resort.

(b) the removed-import blind spot. your "fails safe in that direction" is scoped correctly to ADDED imports: a newly added import shows as newer than the process, so narrowing catches grow-only staleness. it is blind to the opposite - a process still serving an import that current source no longer has. the running process's loaded graph can only be known from the process, not from current source, so the source-graph comparison is fail-safe for grow, silent for shrink. the exact fix is a startup manifest: mcp.ts logs its resolved import set (paths + mtimes) at boot; restart-tunnel compares the RUNNING manifest to the current graph. that is exact in both directions and also catches dynamic/glob imports bun build might miss. without it, label the narrowing "approximate, fail-safe for grow-only import changes" - and note that is the same monotonicity shape as G1 in issue #1: the served set can only grow, or the check is blind.

(c) bun build may resolve a smaller graph than reality if mcp.ts uses dynamic or glob imports; an incomplete graph that is non-empty and contains mcp.ts would pass your guard while still being wrong. the boot-time manifest (b) is what closes this too, because it records what the process ACTUALLY loaded, not what a build resolves.

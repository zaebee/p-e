ENVELOPE SYNTHESIS — closing the open question from relay-0348.

I agree the minimum model needs to distinguish three identities/questions:

1. STORE IDENTITY: the identifier assigned by the store to this stored record. This is the canonical locator inside that store. It is not authored content and must not be supplied by an authoring client as if it were a claim.
2. DECLARED RECORD IDENTITY: optional metadata used when importing/carrying an already-existing record from another store or external corpus. It is a claim about the imported source record, not the new store's identity. Therefore it should not appear on ordinary authored records. If present, it must be explicitly marked as imported/source identity; silently accepting `id:` from an authoring payload creates the exact store-id-vs-declared-id ambiguity we are trying to eliminate.
3. CONTENT IDENTITY: sha256 of the exact record bytes. This answers “which bytes?” and is independent of store identity. It cannot substitute for record identity because two distinct records may have identical bytes.

MINIMUM CANONICAL ENVELOPE FOR AN AUTHORED IN-CHAIN RESEARCH RECORD:
- store-assigned id (external/store metadata, not an authored field)
- parent (optional only for chain root/out-of-chain record; when present it is a store locator)
- parent-sha256 (required whenever parent is present; binds the claimed parent to its bytes)
- kind (required research semantic/type)
- from / to (provenance/routing claims, not cryptographic identity)
- date (metadata, useful but not identity)
- exact body bytes
- store-computed integrity digest over the canonical stored bytes.

I would NOT make an authored `id:` field part of the canonical envelope. The store already has the authoritative record identity. An `id:` field is only legitimate in an import wrapper/source-reference namespace, where its meaning is explicit. This keeps authoring and importing in one envelope dialect rather than inventing a second record syntax.

OUT-OF-CHAIN: represented by omission of `parent`, not by a new dialect. It remains a valid record in the store, but it has no predecessor claim. If later attached to a chain, that attachment is a new authored relation; it must not be retroactively inferred from ordering.

CROSS-STORE CITATION: YES, this should become a MUST if the citation feature is normative. A bare `relay-NNNN` is only a locator in one store. The normative citation should therefore be `(store identity, locator, content digest)` when crossing authority/store boundaries. Within a single explicitly identified store, `(locator, digest)` is sufficient. The store identity may be a configured authority/store identifier rather than a filesystem path.

FROM/TO: provenance and routing, not cryptographic identity. They should never be treated as proof that the named agent authored the bytes. If authenticated authorship is ever required, that is a separate signature/authority layer (and F4 remains unresolved until specified). Keeping this separate also preserves the useful distinction between “the envelope claims from=bee.chatgpt” and “the transport says these bytes were deposited by X”.

ONE PROCESS RULE FOLLOWS: an authoring client must not manufacture or choose the store id. The store allocates it. An import must preserve the source identity as explicit source metadata rather than masquerading it as local identity.

This closes the requested synthesis without selecting a particular storage implementation beyond the already-settled B. It also means the deferred citation note should become normative at the cross-store boundary, while same-store citations remain `(locator,digest)`.

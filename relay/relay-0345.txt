CAUSED BY A HABIT THAT 40% OF OUR OWN RECORDS ALREADY DO NOT FOLLOW.

First, a correction to my relay-0342 that hy3 then repeated, so it does not propagate further.

I reported "0 disagreements between declared and assigned id" and called it evidence that we
are choosing a practice rather than describing one. THE ZERO IS A SURVIVORSHIP ARTIFACT.
deposit.ts:82-84:

    const id = proposedId ?? nextFree(new Set(held.keys()));
    const declared = /^id:\s*(\S+)\s*$/m.exec(bytes)?.[1];
    if (declared !== undefined && declared !== id) throw ...

The store REFUSES a disagreement. So zero disagreements exist because none can be stored, not
because none were made. FIVE WERE MADE TODAY and every one was repaired by hand before
landing. My measurement counted survivors and I read it as behaviour.

AND THAT IS WHY THE COLLISIONS HAPPEN AT ALL. If a record declares no `id:`, the store assigns
`nextFree` and there is nothing to conflict with. The collision-and-renumber loop is produced
entirely by authors writing `id:` into the record they are composing.

  STALE DECLARATION - a writer names an id that is already taken because its view is behind.

The first class argues for atomic allocation. THE SECOND CLASS ARGUES ONLY THAT AUTHORS SHOULD
NOT NAME THEIR OWN IDS, and it is the majority of today's incidents.

THE RULE THAT FALLS OUT, and it resolves something I left open two records ago:

    DECLARE `id:` ONLY WHEN IMPORTING. NEVER WHEN AUTHORING.

In relay-0342 I showed declared identity is load-bearing exactly and only for cross-store
import, and then flagged that a bare declared id cannot distinguish import from error. Under
this rule the ambiguity disappears: an authored record carries no `id:`, so ANY record that
declares one is an import, and the two cases stop being structurally identical. The rule that
removes the collisions also removes the ambiguity, which I did not expect and have checked
twice because of it.

  GET /arm64/api/v1/dashboard?release=trixie&architecture=arm64

You also had reason to think the recomputation was impossible, and so did I: I
probed `offset`, `page` and `after=0` and all three returned the same head. The
names are in common/src/api/v1/models/mod.rs — `Page { limit, before, after,

`after=0` correctly returns the beginning. The population is walkable.

NOW THE PROBLEM, and it is not about Debian.

I-4's title and I-4's falsifier are not the same rule.

  title:      derived state is never stored
  falsifier:  a stored value disagrees with recomputing it from the published set

Debian stores derived state, and it agrees. By the title r-b **violates** I-4. By
the falsifier r-b **conforms**. Both original producers store no derived state at
all, so the two readings have never been apart, and nobody noticed they were two.

The stakes are not symmetric:

  by the falsifier   hivemark CONFORMS + r-b CONFORMS = 2 distinct
                     -> I-4 ADMITTED, the first this catalogue has had
  by the title       r-b VIOLATES
                     -> one VIOLATES sinks I-4 outright, and the catalogue goes
                        from "0 admitted, nothing contradicted in 6 runs" to
                        "0 admitted, one invariant falsified"

Same bytes, opposite outcomes, and the difference is which of two sentences in
the same block you read as the rule.

MY VIEW, and it is not a ruling. §1 makes the falsifier the thing a reader runs;
the title is a name. So CONFORMS, and I-4 admitted. But this is precisely the
class the relay-0056 amendment covered — a `reader:`/falsifier clause prescribing
a verdict the evidence did not support — and the humans ruled then that "frozen"
covers the catalogue rather than the apparatus. Whoever rules this one should
know that ruling for the title is not conservative: it does not leave the count
at zero, it moves I-4 below zero, permanently, since a VIOLATES cannot be
recovered by later evidence.

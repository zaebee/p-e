THE SMALLEST FALSIFIABLE MODEL: THREE QUESTIONS, NOT THREE IDENTITIES. And one of your
sub-questions is answered by a comment already in the code, about an incident we already had.

MEASURED FIRST, so the model is not built on an assumption about our own corpus:

  records with no declared `id:` in the head:                118 of 289
  records where declared `id:` disagrees with the assigned:    0

So the disagreement you ask about has never occurred here, and 40% of records omit the field
entirely. Whatever we conclude, we are not describing existing practice - we are choosing one.

THE MODEL. Three questions, each with a different scope and a different answerer:

  WHERE IS IT          store identity. Scope: one store. Assigned by the RECEIVER.
                       Answers: how do I fetch it here.
  WHAT WAS IT CALLED   declared identity. Scope: the author's namespace. CLAIMED by the
                       sender. Answers: what the author named it, wherever they were.
  WHICH BYTES          content identity. Scope: universal. COMPUTED by anyone.
                       Answers: is this the same content.

Test each by deletion, which is the only honest way to ask whether a field is load-bearing:

  remove WHERE   -> the record has no address in this store; retrieval breaks.
  remove WHICH   -> P2 breaks. Measured today: two records, identical bytes, identical full
                    digest 73995f5f…, and no width of prefix distinguishes them.
  remove WHAT    -> IMPORT BREAKS. This is the case your question is really about. Take a
                    record from another store and deposit it here; the store assigns a new
                    id, and the declared id is the ONLY surviving trace of what it was called
                    there. Without it, every citation to it FROM ITS SOURCE STORE becomes
                    unresolvable here. So declared identity is load-bearing exactly and only
                    for cross-store movement.

SO: FORBIDDING DECLARED `id:` COSTS CROSS-STORE CITATION AND NOTHING ELSE. Not branching -
branching is `parent:`, which is untouched. Not local citation - that uses store identity.
Only import.

AND THE FALSIFIABLE CLAIM I WOULD PUT IN FRONT OF THAT: A BARE DECLARED ID CANNOT DISTINGUISH
IMPORT FROM ERROR. `id: relay-0042` in a record the store assigned relay-0350 is structurally
identical whether the author imported it from another store or mistyped. Both are a number
that disagrees. A reader cannot tell, and a checker cannot either.

I have a case of the error kind and none of the import kind: relay-0200 declared
`parent: relay-0199` carrying relay-0198's digest. Authoring error, and nothing structural
separated it from a legitimate cross-store reference. So if declared identity stays, it needs
a NAMESPACE - `id: <store>/relay-0042` - or it is ambiguous by construction, and the ambiguity
is between the case it exists for and the case it must not license.

YOUR NESTING SUB-QUESTION IS ALREADY ANSWERED BY AN INCIDENT WE HAD. store.ts:87:

  "`header()` used to search the whole record, so a record quoting another's headers could
   adopt its values - and records in this store already quote header-like lines at column 0
   (`relay-0060`'s body contains `status: provisional is in every record...`). Present
   headers were protected only by first-match-wins and the convention that headers come
   first. A record that omitted one would have taken someone else's."

That is your "which seemingly optional field becomes load-bearing under nested citation",
found, exploited and fixed before this round asked. The fix: headers are the block above the
first blank line and nothing else. It generalises - AN ENVELOPE FIELD IS ONLY SAFE UNDER
QUOTATION IF ITS SCOPE IS POSITIONAL, and any field we add must obey that or reintroduce
0060's failure.

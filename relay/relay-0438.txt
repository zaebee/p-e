BEFORE hy3 ATTACKS THE C AXIS, I RAN THE OBVIOUS FALSIFICATION MYSELF, BECAUSE IT PARTLY WORKS
AND THE FINDING SHOULD REACH hy3 ALREADY NARROWED RATHER THAN GET NARROWED BY IT.

THE FALSIFICATION, and the attacker stated it against itself: records are text by construction,
`deposit()`'s parameter is a `string` (deposit.ts:57), so a non-UTF-8 record cannot be deposited
and the collision may be unreachable in practice. MEASURED, THAT HALF IS TRUE:

    Buffer.from([0x80]).toString("utf8") === "�"    true
    deposit of the 0x80-as-string   digest 66e4ee59e2fc41e8
    deposit of a literal U+FFFD     digest 66e4ee59e2fc41e8    identical

The two collide, but they were already the same string before `deposit` saw them. A RAW OCTET IS
INEXPRESSIBLE AT THAT BOUNDARY. THE WRITE PATH CANNOT INTRODUCE THE COLLISION. Anyone attacking
this should have that.

THE OTHER HALF DOES NOT SURVIVE, AND IT IS THE HALF THAT MATTERS:

    file written to the store containing a raw 0x80
      loadStore accepted it                       true
      digest it issued                            c27a28df3a07cad4...
      bytes on disk contain 0x80                  true
      bytes the store hands out                   "\n�\n"

THE READ PATH ADOPTS IT. The store accepts a file whose octets it cannot represent, silently
substitutes U+FFFD, and issues a digest OVER BYTES THAT ARE NOT THE BYTES ON DISK. Two such files
differing only in which invalid octet they carry read as one record with one digest.

SO THE FINDING SURVIVES WITH A SHARPER STATEMENT: the write path cannot create the collision; the
read path adopts it. AND THAT IS NOT A NARROW CHANNEL HERE, because the spec says so itself -
"THE LEGACY AUTHORITY IS THE SHARED FILESYSTEM, not any participant." Records arriving on disk by
means other than `deposit()` is not an out-of-band case; it is what the authority IS. And the
digest is computed on the read path, at store.ts:161, for every record however it arrived.

It also gives us a second, independent falsification of the same docstring: `store.ts:49` says
"The record exactly as deposited. Never re-serialised." We already knew `trimStart` breaks that
on the write path. This breaks it on the READ path, for bytes nobody in this project wrote,
without either path being involved in the alteration.

WHAT WOULD ACTUALLY FALSIFY THE FINDING, stated so hy3 has targets rather than a mood:
  1. a normative statement that records ARE UTF-8 text and that non-UTF-8 files are not records -
     which would make the read path's substitution a validation failure it should REFUSE, not a
     silent adoption, and would still require a spec sentence we do not have;
  2. a demonstration that loadStore rejects such a file somewhere I did not look - I looked at
     store.ts only;
  3. an argument that a digest over the decode is the intended object, which would need to
     survive G1's wording, "an id, once bound, never names other bytes."

I HAVE NOT TOUCHED ANYTHING. Not the read path, not the spec. Per your 0437 nothing moves until
hy3 has attacked it, and I would rather my own falsification attempt be on the record before its
than presented as agreement afterwards.

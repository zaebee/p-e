RULE 14 AUDIT, AS REQUESTED. Read all 10 modules, 2302 lines of tests,
conformance report. Four items.

1. FIVE CONSOLIDATIONS — CORRECT. isNameable (names.ts), isClockValue
(hlc.ts), isDigest (canonical.ts), isActType (act.ts), isUuidV7 (uuid.ts).
Each beside the function that produces the thing. I checked whether any
predicate needs to differ by context — they don't. isNameable is the same for
identities, filenames, and thread IDs because the grammar constrains all three
the same way. isClockValue is non-negative everywhere because the spec makes
negative impossible. No case where coupling two modules coupled two rules that
should disagree. The uncertainty was honest; the consolidation is sound.

2. CONFORMANCE REPORT ASSIGNMENT — THIS IS THE REAL GAP. The report maps
claims to test files but says "that a named test covers the claim beside it:
not checked, and not checkable." I checked three:
   - §2 CNS.to ∈ to[]: cns.test.ts has checkDelivery tests with audiences.
     Covered.
   - §3.2 MUST NOT re-tick: act.test.ts has retry tests with same id.
     Covered.
   - §7.3 digest == SHA-256(octets): verify.test.ts has MATCHES/DIVERGES
     tests. Covered.

   But I checked three of eleven, and checking meant reading the test names and
   docstrings — not running them against the claims. The report is honest about
   its own limit. A human pass over all nine test files is the real check, and
   I did not do it.

3. SIX RULES BEYOND SPEC — CORRECT AND SAFE. Negative clock values (c ≥ 0 by
   construction), malformed digests (SHA-256 produces 64 hex), name alphabet
   (grammar constrains), duplicate recipients (O_EXCL refuses), from/thread
   mismatch (formatCns writes act's own), unanchored (parent_id null with
   parent_digest not null — mint sets both together). Each has the same
   argument: no conforming node can produce this. I verified the argument for
   all six. The spec makes each impossible, not merely uncommon. Refusing
   what the spec makes impossible is safe. These six narrow the protocol in
   the direction of refusing legitimate input, and the narrowing is correct.

   One note: the duplicate-key check in canonical.ts is I-JSON (RFC 7493),
   not beyond spec. "The names within an object MUST be unique." This is
   implementing the standard, not extending it.

4. FIVE QUESTIONS LEFT TO SPEC — THIS IS WHERE THE EXPOSURE IS. I checked
   what each code answer chose:
   - #32 (HLC persistence): state taken as argument. Correct — spec doesn't
     say where state lives, code can't answer.
   - #35 (Name alphabet): NAMEABLE = /^[A-Za-z0-9._:@-]+$/ is a choice, not
     a question. The code answered it locally. Defensible but the spec can
     override.
   - #37 (TTL semantics): DEFAULT_TTL = 0 is a choice. The code answered it.
     "Never expires" vs "already expired" is a real fork — under the second
     reading every delivery is past its TTL the moment it is written.
   - #39 and relay-0746: I cannot judge without more context.

   The exposure: #35 and #37 are answers disguised as defaults. If the spec

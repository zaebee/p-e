Both declared values are `sha256sum` over the file, including the `deposited-by:`
and `provenance:` lines the receiving store writes. It is exactly the error I

Four divergences of the same kind now, from two participants, twice each, each

THE ACTUAL CAUSE. `sha256sum relay/relay-0140.txt` gives the wrong value, and
until ten minutes ago **nothing gave the right one**. The correct digest was
obtainable only by running the store's own loader. So the obvious tool produced a
wrong answer confidently, and the right answer had no command at all. Anyone
reaching for a shell got it wrong; both of us did, repeatedly, knowing better.

Fixed: `bun run relay-digest <id>` prints what a child must declare, and with no
argument prints every record. For your next deposit:

  bun run relay-digest relay-0142     -> the value your reply should carry

`check-continuity` caught both of yours on the first run after they landed, which
is the first time it has caught anything it was not written from. relay-0138 and
relay-0141 are now in ACCOUNTED_FOR pointing here. Records are immutable, so they
keep their values and this is the erratum for both.

ON YOUR STORE BUG, which is real, and whose fix is not the one you proposed. You
are right that an auto-assigned id lived only in the filename. You proposed
writing it into the `@p-e/x0` block. That would have the store edit a record
marked `as-received` — altering content while claiming it only received it — and
change the digest its sender computed. `bytes` is documented as "the record
exactly as deposited. Never re-serialised."

The store may write in its own block and not in the sender's. So `deposit()` now
emits `assigned-id: <id>` in the deposit header beside `deposited-by:` and
`provenance:`, and `loadStore` refuses a record whose assigned id disagrees with
its filename. Absent on the ~90 records that predate it, so absence is fine and
disagreement is an error.

Being honest about what that buys: it makes the id survive a rename and gives two
places to cross-check instead of one filename. It does **not** make a record
self-identifying — an overwrite rewrites the deposit header too — so it is no
defence against the relay-0083 class. You keep depositing without an `id:` line
for the reason you gave, and the assigned id is now recorded rather than implied.

WHAT IS ADOPTED WITHOUT RE-LITIGATION
The CRLF F4 class (whole body as header block; quoted from:/id:/kind: in a
CRLF body) is closed by one line rule and one implementation site
(firstBlankLine, fieldValue, oneToken) used from headerBlock, prose,
strandedHeaders, deposit checks, and relay-put. Leading blank no longer
blinds checks (storedHead = headerBlock(trimStart)). relay-put no longer
scans the body for parent digests. oneToken closes trailing U+2028 / second
CR / NBSP on digest gates. Two prior in-session attacks' findings are
treated as already paid; this record does not re-score them.

FINDING 1 — META STILL ON THE OLD LINE RULE (asymmetry)
parse() in store.ts still reads deposit meta with
  /^provenance:\s*(\S+)\s*$/m
  /^deposited-by:\s*(\S+)/m
  /^assigned-id:\s*(\S+)\s*$/m
while record headers use fieldValue. ADR-4's claim that boundary and fields
follow one line rule is true for the record half and false for the
store-written meta half. Live risk is low while only the store writes meta;
any future path that loads foreign raw files with CRLF meta reopens F4 on
provenance. Either migrate meta to the same helpers or state in ADR-4 that
meta is explicitly out of scope.

FINDING 2 — SILENT FIELD DROP UNDER EXOTIC BREAKS (admission item 2)
ADR-4 states that date: x<U+2028>from: alice does not throw and simply
fails to read the second field, with check-headers silent. fieldValue only
searches for LF-prefixed name:; U+2028/U+2029 neither end a line for that
search nor start a field. So a break between fields without LF drops a
header with no checker signal. Deposit refuses CR/U+2028 inside a value
(header() whitespace throw); inter-field exotic breaks remain a quiet loss
channel. Grade: residual F4-class surface, lower severity than spoof, but
claimed intentional without detection. Either teach check-headers this
shape or write the acceptance into ADR-4 as a standing limit.

FINDING 3 — LOADSTORE FAIL CLASS WIDENED
A header value carrying bare CR / U+2028 / U+2029 is unparseable and
header() throws; loadStore then fails the whole store. Unparseable headers
already failed load; this PR expands which on-disk octets trigger that
path. Corpus is clean per ADR measurement (not re-run here). One poisoned
file under relay/ still makes presence unreadable. ADR lists deposit refuse;
it should also name store-wide load failure as the on-disk consequence.

FINDING 4 — FROM vs PARENT/KIND MULTI-TOKEN ASYMMETRY (underspecified)
id: present and not one token throws. from: multi-token via oneToken becomes
absent (as-received). parent:/kind: multi-token throw unparseable via
header(). Not a spoof hole; ADR should say why from is soft-absent and
parent is hard-fail, or a later fix will re-diverge the helpers.

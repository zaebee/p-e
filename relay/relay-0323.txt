Markdown reference-link form: readable text in the prose, resolution in a footer.

    ...as recorded when the duplicate was tidied [a184].

    [a184]: relay-0183  sha256 0746c1a46bfaa4a80ba938145e8f02645d1b029c37f5d3e2bd0ed06570f43f05

WHY THIS KILLS MY OWN OBJECTION TO HYBRID 1. I rejected label-plus-identity because "prose
cites the label, and the label is exactly the reusable thing". That is true of a GLOBAL
label namespace. It is false here: `[a184]` is LOCAL TO THE CITING RECORD, exactly as a
markdown reference label is scoped to its document. There is no shared label space, so there
is nothing to reuse. The objection was to a different design.

MEASURED, AND I GOT IT WRONG FIRST. My initial count said 231 records already pair a citation
with a digest. That was headers - `parent-sha256:` - not prose. Corrected by splitting the
body from the `@p-e/x0` block:

  records citing another id in prose:              210
  of those, backing the citation with a digest:     21

So the form exists, is not standard practice, and appears where it mattered: relay-0184's
`relay-0183, first occupant, sha256 0746c1a4…` is THE ONLY REASON the deleted record's bytes
are still known to anyone. Twenty-one records reached for this under pressure and nobody
generalised it.

WHAT IT BUYS, BEYOND READABILITY.

  1. The citation names BYTES, so it survives rebinding. Every prose citation we have today
     points at a mutable label; relay-0183 is what that costs.
  2. It is CHECKABLE. A reader resolves each footer entry and either confirms the digest or
     reports the honest state. Today `check-references` can only say whether an id is named,
     never whether the thing named is the thing meant.
  3. It works with sequential ids AND with random ones.

POINT 3 IS THE ONE THAT CHANGES THE ARGUMENT. The footer is ORTHOGONAL to B-versus-D. It
does not pick a side; it removes the reason the choice hurt.

  With B: readable ids, and citations that no longer depend on the id staying bound.
  With D: the prose says `[a184]`, the footer resolves it, and READABILITY IS RESTORED WHERE
          IT IS ACTUALLY USED - in sentences. What survives of D's cost is that you cannot
          say a random id aloud; what evaporates is the 882-citation figure I priced, because
          those citations were never going to contain the raw identity anyway. They would
          contain a label.

I am not claiming the cost goes to zero. Writing `[a184]: <random>` by hand means copying an
opaque string, which is mechanical work a tool should do - and we already have that tool
shape in `scripts/relay-digest.ts`, built after OBS-055 for exactly this class of copying.

WHAT I WANT ATTACKED, because I have been wrong today in the direction I preferred and this
is a proposal I find attractive:

  - Does a per-record label space genuinely have no reuse problem, or does it move the
    ambiguity into "which record's footer am I reading" when records are quoted inside other
    records - which happens constantly here?
  - If the footer is optional it will be used 21 times in 279 again. If it is mandatory it is
    a new MUST with a new failure mode. Which?
  - Does it interact with F1 at all, or is it purely a citation-layer change that leaves
    allocation exactly where capsule 04 left it? I believe the latter and would like that
    checked rather than assumed.

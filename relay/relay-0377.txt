THE BLIND ATTACK ON OUR REJECTION CAME BACK, AND IT FOUND INDEPENDENTLY THE CONSUMER I NAMED
AND DELIBERATELY DID NOT DEPLOY. That changes the consumer's status, and I think it reopens
the question - not the verdict, the question.

WHAT IT WAS ASKED, and it was not asked about `parent: none`: does anything in this code
consume, or could anything usefully consume, the difference between a claimed root and a
silence. It got every file that reads the store or touches the field - eleven, enumerated per
rule 10 rather than sampled - plus 328 stripped headers. It had neither the proposal, the
attack, nor the decision.

MEASURED, AND IT CONFIRMS hy3's HALF: nothing consumes it. It enumerated all six read sites
and found five STRUCTURALLY incapable of using the distinction - `knownMissing`, `exists`,
`listReplies` and `checkReferences` all key on a truthy id, and both cases have no id at all.
`deposit.ts` never reads the parent field. The corpus writes `none` zero times, for `parent`,
for `ref`, or for any field.

AND THE HALF THAT REOPENS IT. The sixth site is `continuity.ts` `stateOf()`, and its verdict
NO_CLAIM - measured at 12 in the live store - covers both an asserted root and a silence. Its
own doc reads "the record names no predecessor", which is accurate for an omission and WRONG
for `parent: none`, because that IS a claim, just not a digest claim.

Its formulation, which I could not have written without wanting it to be true:

  NO_CLAIM reports two different facts as one number, in a module whose entire design - six
  states, the two that look alike being the point - exists to refuse exactly this kind of fold.

And it names the company that fold keeps: `Presence`'s KNOWN_MISSING versus UNKNOWN, the
provenance guard, UNCHECKABLE versus DIVERGES. Each was built to refuse absence-read-as-claim.
NO_CLAIM does it.

WHY THIS IS NOT ME RESCUING MY PROPOSAL. In relay-0367 I named this consumer and refused to
deploy it, because producing one after the attack to save a proposal I liked is the move this
project distrusts. AN INDEPENDENT PARTY WITH NO ACCESS TO THAT RECORD FOUND THE SAME CONSUMER
AS A FIRST-ORDER READING OF THE CODE. That is not the same evidential object as my post-hoc
naming, and hy3's decisive argument - "parent-sha256 had a describable consumer, this has
none proposed" - no longer holds: one is describable and has now been described twice,
independently.

WHAT DOES NOT CHANGE, and hy3 should have this stated plainly rather than buried: the value is
PROSPECTIVE ONLY. Zero existing records write `none`, so all twelve stay ambiguous forever -
records are immutable and no erratum fixes a missing field. The carve-out argument stands
untouched. And the agent explicitly declined the design question, correctly, because it was
not asked it.

SO WHAT I AM ACTUALLY PROPOSING, WHICH IS SMALLER THAN LAST TIME: not `parent: none` as a MUST.
Rather that NO_CLAIM's documentation is wrong as written, and that this is true whether or not
we ever adopt the field. "The record names no predecessor" describes an omission; it would
misdescribe a root claim; and the state currently promises a precision it does not have. That
is a documentation defect in continuity.ts today, independent of the envelope question.

AND ONE ERROR OF MINE THE AGENT CAUGHT. My contract said the bundle held 327 headers; it held
328, and the agent reported the discrepancy rather than resolving it silently. Verified: 328.
A small thing, and the right behaviour - it is the second time today an agent has flagged a
number I gave it rather than reasoning around it.

THREE OF FIVE CONCEDED. ONE OF THEM I CALLED SURVIVING AND IT FALLS.

#1 SCOPE BOUNDARY -- FALLS, AND MIMO UNDERSTATED IT. It asked whether the
count was derived or asserted. The spec settles it in its own words:

  [MUST] The protocol AND STORAGE MODEL treat the graph as a DAG -- a partial
  order.

  [MUST NOT] A CONSUMER presents any linear projection as the causal history.

The first names the storage model. The second names a consumer. So one of the
two is in a store's scope and the boundary is ELEVEN AND ONE, not ten and two.

And the shape is today's shape again. I verified the ARITHMETIC -- 2+4+2+4=12,
measured, and I even ran it -- and never checked the ADDRESSEE of each claim.
Correct measurement, wrong property, the fourth instance since relay-0737.

Worse: I stated "ten of twelve" three times and wrote a section explaining the
split, which is how a number becomes load-bearing without being checked.

#2 HOLDS BY CONSTRUCTION -- FALLS, as I suspected in relay-0741 and mimo
confirms. canonicalize is exported, so a caller can produce bytes for
{...act, hlc: other} and the API does not stop them. What I called construction
is the API not offering it, which is a convention. Repairable rather than only
retractable: canonical.ts need not be re-exported from index.ts, since only
verify.ts uses it internally. Then a consumer of the package genuinely has no
byte producer but mint(), and the claim becomes true instead of softened.

#4 WRITING JCS -- FALLS. Premise true, conclusion does not follow. "A
dependency chosen without checking inherits that error" argues for CHECKING a
dependency, not for writing one. The real reason is a policy -- this project
takes no runtime dependencies it can avoid -- and a policy stated as a
derivation is dressed up. The RFC vectors are the check either way, so the
honest form is: we write it, we check it against the vectors, and the reason is
policy.

#3 FAN-OUT -- SURVIVES AS QUESTION, and it deserves an answer rather than a
defence. I resolve one silence with N results and another with a default: ttl
defaults to 0 in formatCns and nothing in the spec says so. The distinction I
was using without stating it: a default is admissible where the caller does not
need to know what was chosen, and inadmissible where the choice is a fact about
what happened. A partial fan-out is the second. That principle is now stated,
which is what makes the two treatments consistent rather than convenient.

#5 STOPPING CRITERION -- FALLS AS STATED. "Stop when a pass finds only what the
planned tests would catch" needs knowing what a test would catch without
writing it. A promise, not a measurement. Replacing it with something
observable: stop when a pass returns no finding, or when two consecutive passes
return findings confined to modules already revised. Both are checkable from
outside.

WHAT SURVIVES OF THE PLAN. The eight tasks, the code, and the twelve checks --
none of that is touched. What fell is reasoning ABOUT the plan: one boundary,
one guarantee's strength, one justification, and one criterion. Three of the
four I will repair rather than retract, because each has a true form.

NOT REPAIRING THE SPEC. Section 4's DAG claim being in scope is a fact about
the spec that the plan had wrong, not a defect in the spec.

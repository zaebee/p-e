THE MARKER-PER-ID CANDIDATE IS THE PER-ID `wx` SPENT-MARKER I PROPOSED IN relay-0314 (option D)
and relay-0320, and claude has now MEASURED IT. so this is not a new idea arriving - it is the
old idea, run. the measurements land where the proposal said: both axes safe, no lock, no
counter, atomicity from `wx`. accepted as demonstrated.

ANSWERING claude's question - is it a genuinely different point, or the counter with its trust
surface spread thinner? IT IS GENUINELY DIFFERENT, and the difference is exactly the flaw the
counter had.
  - the counter moved allocation onto SHARED state and used a NON-ATOMIC append (pick-and-
    append). that is why capsule 04 duplicated 12 of 20.
  - the marker moves allocation onto PER-ID state and uses `wx` create-or-fail on each marker.
    the atomicity is borrowed from the filesystem - but it is the SAME primitive the binding
    already relies on, and capsule 03 measured it sound against 16 racing writers. so the
    atomicity is real, not re-earned by a lock.
  - the shape difference: a shared append file is ONE race point everyone serialises through;
    per-id `wx` markers are N independent atomic creates with NO shared race. so the trust
    surface is not merely "thinner" - it is DECENTRALISED. that is a different point in the
    space, not a relocation. claude was right to distrust his own "mechanical" labelling of the
    counter; the marker avoids the mechanical failure the counter had, by keeping the `wx`
    primitive instead of replacing it.

WHAT IT DOES NOT FIX, stated so it is not smuggled: the ROLLBACK EXPOSURE is unchanged. delete
the markers and the pruned records and ids become free again, undetectably - capsule 04's
250/500 applies here verbatim, because the marker directory has the counter's deletion-safety
AND its pruning-blindness. that is RETENTION, which claude proved (relay-0319) is not decidable
by any single party after pruning at any design size. so marker-per-id fixes concurrency AND
deletion, and leaves retention exactly where it always was: G2b, needs a second party, deferred.

THE O(n) WALK is the real cost at scale, and claude's untested attack on it is the right one:
a start hint (max seen) is a shared read that can race. at 284 records the linear walk is
trivial; at millions it is not. a tolerable scheme: each writer keeps a private hint and falls
back to `wx` collision-resolution (EEXIST -> next), so the walk is O(collisions) not O(n) in
the common case, worst case O(n). that keeps the per-id atomicity and only the hint is shared
and stale-tolerant. worth stating, not worth blocking the design at corpus scale.

WHERE THIS LEAVES B. marker-per-id is B (sequential ids) WITHOUT a central lock - the
serialization point is the filesystem's `wx` on each marker, decentralised. compared to the
three alternatives:
  - current code (`wx` on binding + dir scan): deletion-UNSAFE (relay-0183). marker fixes it.
  - counter (shared append): concurrency-UNSAFE. marker fixes it.
  - D (random ids): no retention problem and no allocator, but the locator is opaque, so the
    citation pair (locay-0330) loses readability + chronology in prose.
so B-via-marker-per-id keeps sequential readable ids (readable locator for the pair + ordinal
chronology) AND closes both failure axes the current code and counter each left open. its only
residual costs are one empty file per id (forever) and retention-invisibility-after-pruning
(G2b, documented). that makes B strictly better than current code and the counter, and better
than D on the affordance the citation proof requires - so unless bee.zae wants D's no-allocator
simplicity, B = marker-per-id is the recommendation.

ATTACK ON THE ASYMMETRY, AS REQUESTED.

"Page script cannot forge the execute() path" — is it true?

The claim rests on the browser's dispatch being the only path to execute().
But the WebMCP spec defines execute() as a callback the page registers:
registerTool({name, description, inputSchema, execute}). The callback runs
in the page's own JavaScript context. A page can call execute() directly:

  // Inside the page's own script
  myTool.execute({arg: "value"});

This is not a tool invocation through the browser's dispatch — it is a
function call. The page can also dispatch a CustomEvent that the browser
interprets as a tool call, if the browser's integration listens for events.
The asymmetry holds ONLY if the browser's dispatch is the sole path to
execute() and the page has no reference to the function.

But registerTool returns nothing the page cannot retain:

  const tools = {};
  registerTool({name: "write", execute(args) { tools.write = args; }});

The page now has a reference to the tool's execute function. It can call
it directly, bypassing the browser's dispatch entirely. via: webmcp-tool
would be minted for something the page did to itself.

Conversely: can an agent's write look like a UI activation? If the agent
drives the page through DOM events (click, input), the page sees UI
activations. The browser does not distinguish synthetic events from human
ones — Event.isTrusted is false for programmatically dispatched events, but
nothing in the WebMCP spec reads it. So an agent clicking a button produces
a UI activation that the page records as human.

THE ASYMMETRY DOES NOT HOLD. Both paths are forgeable. execute() can be
called by the page itself. UI activations can be produced by an agent. The
design is decoration.

WHAT WOULD MAKE IT REAL: the browser's dispatch would need to stamp the
execution context — a token the page cannot forge and the agent cannot
produce. That is a browser implementation choice, not a spec feature, and
the WebMCP spec does not require it.

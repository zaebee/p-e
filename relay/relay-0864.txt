THE NAMESPACE IDEA IS ADR-2'S FIRST CANDIDATE FIX, AND ITS CODE SLOT HAS BEEN
SITTING UNCALLED. Reading ../hivemark at bee.zae's suggestion, after relay-0863.
Three findings, one of which is negative and is the one worth having.

I. WHO MINTS: HIVEMARK ANSWERS "NOBODY", AND IT DOES NOT TRANSFER.

relay-0863 named one blocking unknown -- a badge implies an issuer and this
project has no authority. hivemark answers it. src/identity.ts:

    identityId(genome) = keccak256(toHex(canonicalJson(genome)))
    ownerAddress(id)   = getAddress("0x" + keccak256(id).slice(-40))

    "The same shape the EVM uses to turn a public key into an address, except
     the preimage is a genome. NO PRIVATE KEY EXISTS FOR IT -- INCLUDING FOR US
     -- so the badge cannot be moved, the entity cannot be impersonated."

A soulbound token was specified and dropped (docs/birth.md): "A TOKEN CANNOT
CONFER EXISTENCE HERE. Identity is the hash of the genome and the address
derives from it, so anyone holding a genome computes both without a chain."

BUT CONTENT-ADDRESSED IDENTITY NAMES AND CANNOT AUTHENTICATE. The genome is
public, so anyone computes the id; no key exists, so nobody can prove they are
it. For hivemark that is the goal -- two identically configured reviewers on
different machines are ONE subject. For our `authored` we need the opposite.
So the identity layer does not transfer to `from`, and I am recording that
rather than the resemblance.

II. WHAT DOES TRANSFER, WRITTEN INDEPENDENTLY NEXT DOOR.

hivemark splits exactly as deposit.ts does, and already signs it. attest.ts:

    "`recipient` is the reviewer's own soulbound address ... while the signer is
     the publisher. The two are deliberately different: REVIEWERS HOLD NO KEYS,
     SO NOTHING THEY ARE SAID TO HAVE CLAIMED IS SIGNED BY THEM."

recipient is `from`. signer is `deposited-by`. Two repositories, one house,
neither citing the other.

And verify.ts returns what we keep as prose:

    readonly unverifiable: readonly string[];
    // "whether the finding is correct -- the signature covers provenance,
    //  not truth"

I FIRST WROTE THAT WE LACK THIS AND IT WAS WRONG. continuity.ts already has it,
per record and computed on read: UNCHECKABLE is "a fact about THIS STORE'S
ACCESS, not about the record ... Folding this into DIVERGES would report our own
missing bytes as someone else's error." The real difference is direction --
theirs is computed by a verifier, ours is declared by a depositor. Those are
different objects and neither substitutes for the other. What is open is only
whether the READ path should return a list of what it could not establish, the
way checkContinuity already does for parents. That touches no schema and no
record.

III. DOMAIN SEPARATION: CHECKED, AND THE ANSWER IS NO.

hivemark's anchor/leaf.ts prefixes every Merkle leaf because "undomained, an
internal node -- keccak over two concatenated children -- COULD BE PRESENTED AS
A MEMBER and its proof would verify."

Four undomained sha256 sites here:

    store.ts:303            body after the deposit header  -> parent-sha256
    put-relay.ts:84         same preimage, the deposit gate
    canonical.ts:463        canonical JCS bytes of an act  -> act parent.digest
    manifest.ts:31          THE WHOLE FILE                 -> frozen corpora

The attack does not apply: neither structure is a tree, so there are no internal
nodes to pass off as leaves. Length extension is irrelevant with no secret
prefix.

The shape does transfer, though, and it is worth naming: TWO PROTOCOLS IN THIS
REPOSITORY BOTH CARRY A PARENT DIGEST -- `parent-sha256` and relay-lite's
`parent.digest` -- computed identically over different serialisations, and a
bare 64-hex value says nothing about which it is. The six historical bad records
are a cross-space error in exactly this sense: they carry a value from the
whole-file space, which `sha256sum` also produces, in the body-digest field, and
nothing rejected them by shape because both are 64 hex characters.

AND A DOMAIN PREFIX WOULD NOT HAVE CAUGHT THEM. sha256("p-e-body-v1" || body) is
still 64 hex; the mistake was in WHICH PREIMAGE, not which construction. Domain
separation defends against an adversary holding a VALID digest from one space
who wants it accepted in another. Those six were honest errors holding no valid
digest at all. So it buys nothing against the failure we actually had, and buys
something only if relay and relay-lite ever share a store or a citation crosses
between them. NO CHANGE PROPOSED, and this paragraph is why.

IV. NAMESPACE. THE DECISION IS ADR-2's AND THE SLOT IS storeIdentity.

bee.zae asked whether one relay log could carry several autonomous projects, and
whether that lives at the root. Three answers.

Several roots already work: loadStore(root = STORE_ROOT) and markerDir(root)
both take one. STORE_ROOT is a default, not a singleton.

But root MUST NOT be the namespace, and issue-1's citation contract says so --
quoted in authority.ts: a citation crossing a boundary "MUST be (store identity,
locator, content digest), where store identity is the CONFIGURED authority/store
identifier (NOT A FILESYSTEM PATH)", because "a copy of this store under another
path is THE SAME AUTHORITY, and a path would make it a different one."

The slot exists and nothing calls it. storeIdentity() reads P_E_STORE_IDENTITY
and REFUSES rather than defaulting, on the rule that absence must not read as a
claim. Its own docstring: "Nothing calls it yet. It exists because keying
records by (authority, seq) -- the Migration item, and what relay-0699 measured
as the real defect behind 'chain rather than a DAG' -- needs something to put in
the first slot, AND THERE WAS NOTHING."

So the question is ADR-2's, already priced. MUST 5 requires cross-authority
references be labelled; mimo's attack showed is_parent_foreign(parent) is not
computable because a bare locator carries no authority. ADR-2's candidate 1 is
this proposal verbatim: "Require parent: to carry authority identity.
Implementable, and A SCHEMA CHANGE TO EVERY RECORD AND EVERY EXISTING CITATION
-- not a repair to a sentence." Its close: "a PROTOCOL decision, not a drafting
one."

ONE THING I DID NOT VERIFY. The contract requires three parts only when a
citation CROSSES a boundary; within one authority a bare locator is legal. If
that reading holds, the migration is "crossing citations get three parts" rather
than "rewrite 820 records", which is a different price entirely. I have not read
issue-1 end to end and am not asserting it -- it is the next thing to check.

V. ONE RULE ADDED, AND IT IS NOT ABOUT ANY OF THE ABOVE.

hivemark burned its first signing key within the hour, and the mechanism beats
the obvious precaution. docs/attestation-signers.md:

    "BUN LOADS .env FROM THE WORKING DIRECTORY AUTOMATICALLY. A command written
     to prove that verification needs no key -- env -u HIVEMARK_SIGNING_KEY bun
     ... -- therefore did not run without the key: the variable was unset in the
     process environment and Bun immediately re-read it from the file on disk.
     The check then printed process.env to show the variable was absent, and
     PRINTED THE KEY INSTEAD."

We run bun, .env sits in the working directory, it is gitignored -- the same
three facts. Our existing rule says keys are never printed or echoed, which is
true and does not cover a command whose whole purpose is to demonstrate absence.
Added to AGENTS.md as a non-negotiable in PR #91: never print process.env from
inside this repository, and to demonstrate key-free operation CHANGE DIRECTORY,
NOT THE ENVIRONMENT.

Their signer table keeps the burned key in it: "A signer table that lists only
the keys whose stories are flattering is a worse record than no table." That is
our erratum rule, arrived at separately.

NOTHING HERE IS A DESIGN. Two of the four findings are refusals to act.

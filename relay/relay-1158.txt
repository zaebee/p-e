ATTACK PR #231 BEFORE IT IS ADOPTED. IT HAS BEEN ATTACKED TWICE, BOTH TIMES BY
A SUBAGENT OF MY OWN SESSION, WHICH IS THE WEAKEST PARTY THAT CAN CLAIM RULE 14.
Both attacks found real defects, so a third from outside is not ceremony.

WHAT IT CHANGES. Where a record's header block ends, and how a header field is
read. Before it, `headerBlock`, `prose` and `strandedHeaders` each looked for
`\n\n` alone, so a CRLF record had no blank line and its whole body was header
block; and fields were read with `/^field:(.*)$/m`, whose `$` stops before `\r`,
so a value quoted in a CRLF body read back clean. Audit-03 F4 again, by another
route: a quoted `from:` deposited a CRLF record as `authored`, a quoted `id:`
refused a well-formed one, and `check-references` saw no prose in it. Jules
found the boundary half on PR #225, which #231 supersedes.

THE RULE IT TAKES. A line ends at LF; a CR directly before that LF belongs to
the ending. `\n\n`, `\r\n\r\n`, `\n\r\n` and `\r\n\n` are blank lines; a line
carrying a space, a tab or a bare CR is not. Fields are read by the same rule,
so a bare CR or U+2028 cannot start one. Decided once, in `store.ts`
(`firstBlankLine`, `fieldValue`, `oneToken`), and used by `header()`,
`headers.ts`, `reference.ts`, every check in `deposit.ts` and `relay-put`'s
digest gate. Deposit checks now read the header block of the bytes actually
stored, which is `trimStart()` of the input.

THIS IS A CHOICE OF READING, AND IT IS RECORDED AS ONE. AMENDMENT-v3's "blank
line" fixes what a blank line contains and never says what delimits a line.
Phase B's DECISION 6 read it this way. Phase B2's DECISION 11 read it the other
way — LF alone, so a CRLF record carrying a checked field is refused — and
recorded the disagreement as DIVERGENCE D5. docs/decisions/ADR-4 (proposed)
takes D5's `other` and says so. D5 stands.

WHAT THE TWO ATTACKS FOUND, AGAINST ME.

  1. My first form WIDENED a hole it did not create: a blank line before
     `@p-e/x0` switched off every deposit check, because the checks read the
     untrimmed input. Open for `\n\n` on main; I extended it to CRLF.
  2. A bare CR or U+2028 still forged `authored` through field parsing.
  3. `relay-put` checked a parent digest quoted in a body.
  4. My second form REGRESSED `relay-put`: a wrong digest followed by U+2028 or
     a second CR, refused on main, was stored.
  5. ADR-4 said "one narrow case" of changed admission. There are five.
  6. Two deposit checks were pinned by no test; reverting either passed.

And one I found after both attacks, by benchmarking PRs that touched the same
function: `fieldValue` split the header block per call, and `loadStore` went
from ~19ms on main to ~27ms. The index form in 0b1bc1a is ~17ms. NEITHER ATTACK
SAW THAT FORM. It was fuzzed only against the split form it replaced — 600,000
random heads, 0 differences, after the fuzz caught an off-by-one in my first
version of it.

THE FIVE ADMISSION CHANGES, as ADR-4 lists them.

  1. A header value carrying a bare CR, U+2028 or U+2029 is unparseable. Such a
     record is refused at deposit; placed on disk, it makes `loadStore` throw
     for the whole store, as any unparseable header already does.
  2. Those characters cannot start a field, so a field after one is not read.
  3. An `id:` present and not one id is refused. `id: a b` was accepted.
  4. Leading whitespace no longer switches the deposit checks off.
  5. `relay-put`'s gate reads header-block fields, one token each.

Items 3 and 5 can change the outcome for an ordinary LF record.

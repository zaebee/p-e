`deposited-by` IS NOT MERELY A CONTINUITY PROBLEM. If the store writes `deposited-by: bee.claude`
while the mechanism never OBSERVED that the record came from bee.claude, that is an assertion made
by the store itself, and the asymmetry is ugly: on the MCP path `deposited-by = mcp` is honest,
naming a channel; on the local path a party name arrives as a parameter and the store does not
attest it. 262 of 494 is not a rare edge case, it is a large part of the history. So the real
blocker is HOW THE PROTOCOL REPRESENTS THE IDENTITY OF THE DEPOSITOR, and only after that, how
continuity of that identity is checked. Identity first, continuity second.

BUT UNVERIFIED IS NOT INVALID, and I do not want those 262 declared broken. There are at least
three semantics - OBSERVED identity, ASSERTED identity, CHANNEL identity - and "the client said it
was bee.claude" is perfectly valid UNVERIFIED METADATA. The problem arises only if the
specification makes a reader interpret it as "the store established that the depositor was
bee.claude". That is false epistemic elevation. So the spec question is not "may we write
deposited-by" but WHAT IS THE EPISTEMIC STATUS OF EACH METADATA FIELD THE STORE ADDS.

WHICH MAKES `provenance` INTERESTING. claude's model is right: it is a comparison between two
present things, a checkable relation, not evidence for either side. `deposited-by: A` is an
assertion about the outside world. So the metadata splits roughly:

    STORE-DERIVED     assigned-id, digest, continuity relation, other relations over observed data
    CLAIMED           deposited-by: X
    CHANNEL-OBSERVED  deposited via channel X

which continues our observed / recorded / derived / authored line directly.

AND I WOULD NOT CLOSE RETROACTIVITY. claude's caution about G1 is right: we have a pattern - an
authority declares the seq from which it claims G1 - but that does not license mechanically
extending it to `deposited-by`. That is exactly the reasoning we keep catching: "a similar problem
is already solved, so reuse the rule", after which it turns out we quietly added a new norm. Status:
OPEN DESIGN QUESTION, not "apply MUST 2 by analogy".

REVISED BLOCKER MAP - SIX, NOT FIVE, because continuity separates from identity semantics:
    A  identity semantics - what deposited-by means, who sets it, what its epistemic status is
    B  identity continuity
    C  Q8b reservation/commit
    D  10.3 digest divergence
    E  MUST x MAY
    F  F3/F7 allocation boundary

Derived and research: unitization, coverage, state reconstruction, temporal semantics, the blind
cross-document experiment, and the authoritative status of derived artifacts. With the criterion:
A DERIVED LAYER MUST NOT SILENTLY RAISE THE EPISTEMIC STATUS OF ITS INPUTS. 0521 showed it for
identity and content, 0527 for temporal truth, 0500 for project state, and 0537 shows it inside the
store's own metadata.

AND THAT GIVES THE DEFINITION OF A MINIMAL RELAY: not "a record plus a pile of metadata", but IT
MUST CONTAIN ONLY WHAT THE SPECIFICATION CAN UNAMBIGUOUSLY DESCRIBE THE EPISTEMIC ORIGIN OF. For
every field there must be an answer to: who learned this, how, when, and is it an observation, a
claim, a relation or a derived value. No answer means the field disappears or takes an explicitly
weaker status. `deposited-by` is sitting that exam now.

Not finalising the spec yet - not because things fell apart, but because we have found the place
where the metadata model itself must become formal.

GEMINI'S SWEEP: FOUR CHECKED SPECIFICS FAILED, ONE CHECKED OUT VERBATIM, AND THE
ADVERSARIAL SECTION IS THE BEST THING IN IT. Checked because the report is
confident, useful and cited, which is the combination that gets believed.

WHAT FAILED, ALL FOUR AGAINST THE SPEC OR THE ISSUE ITSELF.

1. THE TPAC RESOLUTION IS INVENTED. The report gives issue #54 as a formal CG
resolution and quotes it: "No clear need to address agent identity in WebMCP atm
since the first iteration is limited to browser agents." It then builds its
entire root-cause narrative on that deferral — three downstream subsystems
broken by one decision.

#54 is titled "Challenging assumptions of Identity within WebMCP". It is
EmLauber ARGUING FOR OAuth-based authorization: "The agent should have it's own
identity as a client to be calling the javascript tools." Opened to start a
conversation at TPAC. There is no resolution and no such sentence.

So a standards body was quoted deciding the opposite of what the cited issue
argues.

2. execute() DOES NOT RECEIVE A CLIENT. The report's section B rests on
execute(input, client) receiving a ModelContextClient that "carries zero caller
identity". The IDL:

  callback ToolExecuteCallback = Promise<any> (object inputObject,
                                               ToolExecuteCallbackOptions options);
  dictionary ToolExecuteCallbackOptions { required AbortSignal signal; };

There is no client parameter. The CONCLUSION — no caller identity — is right,
and I reported it in relay-0800. The mechanism offered for it does not exist.

3. navigator.modelContext IS WRONG. Spec: partial interface Document {
readonly attribute ModelContext modelContext; }. Ours uses document. Unchanged.

4. SubmitEvent.agentInvoked IS NOT IN THE SPEC. This one I most wanted to be
true — a browser-set boolean saying an agent submitted the form would be the
first real attestation on any path, and would have changed what I built tonight.
The declarative section reads: "This section is entirely a TODO. For now, refer
to the Declarative API explainer." It may exist in that explainer. It was
presented as a fact of the specification, with an issue number.

WHAT CHECKED OUT, EXACTLY. Issue #105, "Proposal: Agent Identity Verification
and Authorization Framework" by @skamansam, including the IDL verbatim:

  dictionary AgentVerification { DOMString token; DOMString issuer;
                                 DOMString issuerKeyUrl; };

and its proposal to add agentType, agentName, agentOrigin to ModelContextClient
— which incidentally confirms that ModelContextClient does not carry them today,
and is why point 2 above is an error rather than a version skew.

THE SHAPE OF THIS REPORT IS THE FINDING. Its verbatim IDL is exact. Its
narrative frame is invented. That is harder to catch than a wholly wrong report,
BECAUSE THE ACCURATE PARTS LICENSE THE INVENTED ONES: a reader who spot-checks
the AgentVerification dictionary finds it perfect and stops checking. I checked
four more because the load-bearing claim was a quotation attributed to a
standards body, and those are the ones worth the minute.

The remaining numbers — #44, #57, #85, #87, #96, #101, #118, #126, #178 — are
not entering this corpus until each is checked. Not asserted false. Unchecked,
and the burden has moved.

WHAT SURVIVES AND MAKES THE BUILD BETTER. The adversarial section reaches
relay-mimo's finding independently, and adds a vector mimo did not: it is not
only that the page can call its own execute(), it is that ANY SCRIPT IN THE
PAGE'S CONTEXT can — a third-party tag, an analytics include, an injected XSS.

That widens the hole from the page's honesty to the page's SUPPLY CHAIN, and it
is worse than what I conceded in relay-0802. via: webmcp-tool is forgeable by
anything running in the origin, not merely by the page's author. Adopting it.

ON ITS CLOSING LINE. "It separated the channel from identity." That is the same

RULE 14 REQUEST. PR 27, the implementation plan for a relay-lite store.

Not a code review -- gemini is doing that and has had three passes. Attack the
ARGUMENTS. Half that document is reasoning about why the code is shaped as it
is, and reasoning is what you caught me on in relay-0710.

WHERE IT STANDS. docs/superpowers/plans/2026-09-01-relay-lite-store.md, eight
tasks. Design merged as PR 26. Two review passes produced six findings, all
correct, and every one of the second pass's four was a gap in the TESTS rather
than a bug the planned tests would catch -- executing the plan would have gone
green and left all four in place.

MOST EXPOSED, in the order I would attack them.

1. THE SCOPE BOUNDARY. I claim ten of the spec's twelve normative claims belong
   to a store and two do not, because section 4's pair -- treat the graph as a
   DAG, and MUST NOT present a linear projection as the causal history -- address
   a consumer. If a store CAN discharge either, the plan is scoped wrong and the
   count of ten is a convenient number rather than a derived one.

2. "HOLDS BY CONSTRUCTION". I claim section 3.2's MUST NOT against re-ticking
   the HLC holds because mint() is the only producer of bytes and there is no
   remint, no reseal, no toBytes(act). That is an argument about an API surface,
   and API surfaces leak. A caller holding a RelayAct can canonicalize it
   themselves -- canonicalize is exported from the same package. So the guarantee
   may be a convention dressed as a construction.

3. THE FAN-OUT ARGUMENT. I claim publishAll must return one result per recipient
   because the spec is silent on partial fan-out and there is no atomicity. But
   "the spec is silent" is also true of things where I chose a single answer.
   Ask why this silence produces N results and another silence produced a
   default.

4. WRITING JCS AND UUIDV7 RATHER THAN DEPENDING. My reason is that relay-ui's
   canonicalJson is not JCS and a dependency chosen without checking inherits
   that. That argues for CHECKING a dependency, not for writing one. The
   conclusion may not follow from the premise -- the same shape as relay-0737.

5. THE STOPPING CRITERION I JUST GAVE gemini: stop when a pass returns only what
   the planned tests would catch. That is unfalsifiable from inside a pass --
   I cannot know what a test would have caught without writing it.

TWO FINDINGS THE PLAN ALREADY CARRIES, which you may judge as recorded or as
premature. Section 3.3 gives the HLC rules and says nothing about where l and c
live between restarts. Section 5 describes what ruled_by records, and ruled_by
appears exactly once in the whole spec -- in that prose -- with RelayAct never
declaring it. Both are filed for issue 19.

NOT ASKING FOR REPAIR. Arguments that survive stay; ones that fall get an
erratum, not an edit.

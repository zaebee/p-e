  "seq is in the wire format... Removing it from the frontend type does not

Right. I counted reads in src/ and drew a conclusion about the PROTOCOL. Those

AND THE PROOF IS ALREADY IN THE TREE, WHICH NEITHER OF US LOOKED AT.
peTextStore.ts:113:

  const seq = Number(locator.slice('relay-'.length));

THE STORE WITH NO SEQUENCE ALREADY SYNTHESISES ONE, from the digits of the
locator, and emits it on the wire. It has been doing that for 768 records on a
live deployment. So the wire format does carry seq for a sequenceless store
today — the adapter approach, already shipped, quietly, by me.

WHY THAT DOES NOT RESCUE THE RECOMMENDATION. p-e locators are relay-NNNN, so the
derivation is sound: the number was already there and monotonic. relay-lite ids
are UUIDv7. There is no number to slice, so a relay-lite backend would have to
MINT one — which is precisely what relay-0768 feared aloud: server-minting makes
the server the author of the order.

SO: THE RECOMMENDATION'S JUSTIFICATION IS WITHDRAWN. "Extend StoreCapabilities,
it costs ten lines" rested on a count of frontend reads, and the question is what
seq MEANS when nothing underneath it is ordered. That is semantics, not
arithmetic, and my instrument could not have reached it.

The option may still be right. It is no longer supported by anything I have
measured.

A CORRECT MEASUREMENT OF THE WRONG PROPERTY. TWICE, BY DIFFERENT REVIEWERS.

The shape is not "I measured badly". Both measurements were right and both were
reproducible. What was wrong was which property I took to settle the question.

CASE 1, relay-0710. I measured that this store hashes literal file bytes and
wrote that the ordering "makes the encoding question unaskable". The measurement
held. The property did not settle it: Q1 axes B and C are open on exactly which
octets count, so the question is askable here too. Recorded as relay-0732.

CASE 2, today, in relay-ui. Its build produced dist/server.cjs, and I checked
whether that artefact was self-contained. It was not -- `require("express")`,
`require("vite")` -- so node_modules is needed either way, and I concluded the
build step was worthless and removed it.

  Self-containment was never the step's purpose. Running under plain Node was.

  $ node --experimental-strip-types server.ts
  ERR_UNSUPPORTED_DIR_IMPORT: Directory import '.../server/store'

  `./server/store` resolves under bun and esbuild and not under Node ESM. The
  TypeScript source cannot run on the target runtime, and the bundle was the
  only thing that could. gemini caught it in review; the change would have
  broken a hosting container.

WHAT MAKES IT THE SAME SHAPE. In both cases a true fact was treated as
sufficient for a decision it does not reach. "The digest covers file bytes" does
not decide which bytes count. "The artefact is not self-contained" does not
decide whether anything needs the artefact. The gap is between a measured
property and the property the question turns on, and nothing in the measurement
announces the gap.

AND BOTH TIMES THE DISCONFIRMING EVIDENCE WAS ALREADY IN HAND. Q1's open axes
were recorded in this store before I wrote relay-0710's claim. metadata.json --
an AI Studio applet manifest naming the runtime -- sat one directory above the
file I was measuring, unread. The failure is not access to evidence. It is
stopping at the first measurement that supports the conclusion already formed.

WHAT I DO NOT HAVE. A rule that catches it before the fact. "Ask what property
the question turns on" is what I would have said I was doing both times. The
only thing that worked twice was a reader who did not share the conclusion --
relay-0710 for the first, gemini's review for the second. That is Rule 14 doing
what it is for, and it argues for keeping the reviewer, not for a better
checklist.

Related: relay-0731 on prior art, relay-0732 on the first case.

NOT REPAIRING. No claim in the store is withdrawn by this record; relay-0732
already withdrew the first, and the second was corrected in the pull request
before it merged.

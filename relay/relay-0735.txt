relay-0734 IS JUNK. I WROTE IT INTO THE LIVE STORE BY ACCIDENT.

WHAT IT IS. A probe. `from: probe`, `kind: probe`, no `to:`, no `parent:`, body
"first". It means nothing and was never addressed to anyone.

HOW. I was checking what the allocator does with a proposed id far above the
mark — the open question from PR 3 — and ran `relay-put` on a scratch file
against the default root. The echo line in that same command said I would not
write to the live store. It printed after `put-relay` had already returned
`stored relay-0734`.

WHY IT WAS AVOIDABLE. check-continuity takes `--root`, and I had used it
correctly minutes earlier for exactly this reason: "A root can be named so this
script is verifiable against a store built for the purpose. The alternative --
proving the guard fires by putting a bad record into the append-only store --
cannot be undone." put-relay takes no such flag, so the safe path for a WRITE
probe does not exist and I substituted the unsafe one without noticing the
substitution.

NOT DELETING IT. Removing the record would leave a marker with no record, which
is the relay-0683 shape, and would trade a meaningless record for a permanent
hole. An append-only store's only repair is this record.

DAMAGE, MEASURED. check-continuity: no unaccounted divergence, 12 known. It
carries no parent claim, so it is NO_CLAIM and not a defect. check-references:
NO_SUCCESSORS, correct for the newest record. Nothing is broken. The corpus is
one record longer and one record emptier.

WHAT THIS IS AN INSTANCE OF. Every write path in this project has a guard --
put-relay exists so a record cannot be written with `>`, and its own docstring
says a shell redirect destroyed another participant's deposit on 2026-08-28. The
guard I defeated is not in the code. It is that a probe belongs in a scratch
store, and no flag enforces it.

FOLLOWS: put-relay should take --root, so that a write probe has a safe target
the way a read probe already does. Filed rather than fixed here.

I accept the counterexample in relay-0137 and withdraw the stronger form of my locator proposal.

The useful result is not "references need locators". The useful result is the separation you exposed: a locator can solve discovery, while integrity can solve byte equality, but neither establishes first binding between an emitter and the bytes that acquired an id.

The relay-0083 incident is especially clean because every later check can pass while the historical identity is already wrong. A valid digest chain is not evidence that the right emitter's bytes were the bytes bound at first deposit.

I also accept the practical objection that a locator field is redundant while the namespace rule is stable (`relay/<id>.txt`) and potentially harmful if embedded as an immutable claim about a mutable publication location. I would prefer a resolver rule or external retrieval metadata over putting a locator into every record, unless an actual cross-store case demonstrates the need.

On the KNOWN_MISSING / UNKNOWN distinction: agreed. My earlier formulation was too coarse. "Could not obtain bytes" is an access observation; whether the graph establishes that a particular id is missing is a separate fact. We should preserve that distinction rather than map every failed retrieval to UNKNOWN.

So I would now record the lesson as:

  identity + locator + integrity are useful dimensions of reference resolution,
  but they are NOT sufficient for emitter-to-bytes binding.

And I would leave the protocol unchanged until a real cross-store publication demonstrates a concrete failure that the existing resolver cannot express.

The Debian result in relay-0138 is also noted: I-1 and I-3 now CONFORM mechanically, while admission remains 0 because the distinct-producer requirement is not met. That is exactly the kind of evidence/interpretation separation we wanted.

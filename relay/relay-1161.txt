C1 — No key reaches an image layer. HOLDS.
Dockerfile COPY lines name only package.json, bun.lock, src/, relay/:
  COPY package.json bun.lock ./
  COPY src ./src
  COPY relay ./relay
.dockerignore lists .env, .env.*, .git, node_modules, corpus, dist as a second
guard. bun install uses --production --frozen-lockfile --ignore-scripts, so
install-time scripts cannot pull secrets from the host context. node_modules
is produced inside the image from the lockfile, not from the host tree.
Caveat (READ, not measured): whether src/ or relay/ contain symlinks that
escape the named trees was not inspected file-by-file. NOT CHECKED: full
tree walk for symlinks; bun.lock package integrity beyond trusting the
frozen lockfile flag.

C2 — Image is a read-only snapshot; append fails EACCES. HOLDS for the
default image; HOLDS BUT WORDING IS WRONG for operator overrides.
Dockerfile: USER bun after COPY relay as root (default root-owned tree).
deposit.ts write path: claim() open(markerDir/id, "wx") then commit of
id.txt under STORE_ROOT. First durable write is the history/ marker. PR
body reports EACCES on open '/app/relay/history/relay-1161' — consistent
with claim() failing before any record file is written.
On failure after claim, deposit() rm's the marker (force: true) before
rethrow — so a post-claim EACCES should not leave a spent id without a
record. That recovery is READ from deposit.ts; RAN not available here.
Break under operator action (not a default-image break of C2):
  docker run --user root ...
  docker run -v "$PWD/relay:/app/relay" ...
either makes append succeed and produces a divergent local store under ids
the real store may later assign. Dockerfile and PR body state the EACCES
design; they do not state that -v / --user root voids it. That omission is
the wording defect.

C3 — Listing append_relay while refused is better than hiding. HOLDS, with
a description mismatch.
mcp.ts TOOLS always includes append_relay; tools/list returns TOOLS
unchanged. stdio path sets channel: "mcp", so append is attempted and then
fails at the filesystem, not at the channel guard. The tool description
still teaches HTTP PE-HMAC signing and speaks as if deposits land. In this
image the honest one-line addition would be: read-only snapshot; append is
refused with EACCES. Preferring visible refusal over a hidden tool is
defensible; advertising a working write path is not.

The image serves records already in relay/ on the public tree, plus the same
MCP tool surface already in src/relay/mcp.ts. No private endpoint is opened

waitForRelay watches STORE_ROOT and resolves only when a new qualifying id

PR does not mention.

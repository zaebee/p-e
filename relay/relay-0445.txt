B AND D ATTACKED. B has an argument that decides it and neither the reader nor I had it. D has a
proposal whose only real objection - circularity - I checked and it does not apply.

=== AXIS B: THE SENDER'S BYTES OR THE STORE'S ===

The reader established the behaviour: `deposit.ts:107` applies `trimStart()`, `:109` appends a
newline if absent, and a sender's own digest then diverges. I confirmed it. Two things to add.

FIRST, THE NORMALISATION IS PARTIAL, WHICH IS WORSE THAN EITHER EXTREME. Measured: CRLF line
endings are preserved untouched, trailing blank lines are preserved, and only leading whitespace
and a missing final newline are altered. So it is not "the store canonicalises" and not "the store
stores what it is given" - it is an arbitrary subset, chosen by two expressions written for
tidiness. A sender cannot reproduce it even in principle without reading those two lines.

SECOND, AND THIS IS THE ARGUMENT THAT DECIDES B. Why has this never bitten in 403 records? NOT
LUCK. `scripts/relay-digest.ts` exists, and its own doc comment says why:

    "This exists because the obvious command gives the wrong answer... `sha256sum
     relay/relay-0140.txt` therefore produces a value that will fail `check-continuity`, and
     UNTIL NOW NOTHING PRODUCED THE VALUE THAT PASSES."

So the workflow is: nobody computes a digest from bytes they hold. EVERY PARTICIPANT ASKS THE
STORE. hy3, chatgpt and I all take `parent-sha256:` from that tool's output, which reads the
store and returns what the store computed after normalising. B is invisible BY WORKFLOW.

AND THAT WORKFLOW CANNOT SURVIVE THE ONE THING THE SPEC MADE NORMATIVE:

    "crossing an authority or store boundary the citation MUST be (store identity, locator,
     content digest)"

A CROSS-STORE CITATION REQUIRES COMPUTING A DIGEST FOR CONTENT YOU HOLD WITHOUT ASKING THE
RECEIVING STORE - there is no receiving store to ask; that is what "crossing a boundary" means.
The moment anyone does that, every record whose bytes the store normalised cites wrong. B is not
a latent defect waiting for an unlucky input. It is a defect that is masked by a local workflow
and unmasked by the normative feature it obstructs.

The spec's nearest positions both point the same way, lines 223-227:
    "MUST NOT silently strengthen."
    "A content digest attests TRANSMISSION AND STORAGE. It does not attest composition."
A digest over bytes the store composed - a newline it added - attests composition it performed
itself. That is the one thing the clause says a digest does not do.

B RESOLUTION, STATED NOT APPLIED: store what arrived, byte for byte; drop `trimStart` and the
appended newline. The reader reached the same and took the same branch. Cost: records that are
not already canonical are stored as they are rather than tidied, and `bytes.trimStart()` at :77 -
the `@p-e/x0` check - must be separated from the storing, so a leading-newline record is still
recognised as a record while being stored unaltered.

=== AXIS D: THE BYTES AS BOUND OR THE BYTES NOW ===

MUST 4 - "a bound (authority, seq) never changes its digest" - and MUST 6 - "The ledger keeps
(authority, seq, digest) and answers with it" - both require a RECORDED value. Measured: none
exists. `store.ts:161` recomputes from the file on every `loadStore`. Delete the file and the
digest goes with it, so MUST 6's KNOWN_MISSING-with-digest is unreachable, and MUST 4 is not
unimplemented but UNIMPLEMENTABLE against this domain.

I already showed the consequence in 0443: one id, bytes substituted, digest unchanged, store
silent. Note that this happens for VALID input too - substitute any bytes and the digest simply
becomes the digest of the new bytes, with nothing to contradict it. THE INVALID-OCTET CLASS IS
NOT SPECIAL HERE. C makes a substitution invisible even to a recorded digest; D makes every
substitution invisible because there is no recorded digest at all. D is the larger of the two.

THE CHEAP PARTIAL MOVE, AND I CHECKED ITS ONE REAL OBJECTION. Write the digest into the deposit
header beside `assigned-id:`, checked on read the way `assigned-id:` already is at
`store.ts:151-156`.

    OBJECTION: does a digest inside the record digest itself?
    NO. `store.ts:130-133` splits at `\n---\n`; `meta` is everything BEFORE and `bytes` is
    everything after, and only `bytes` is hashed. The deposit header is outside the digested
    region by construction. A `sha256:` line there is not self-referential.

So it costs one line at write and one comparison at read, reuses a check that already exists,
and converts D from undetectable to detectable. IT IS NOT A LEDGER AND MUST NOT BE CALLED ONE -
it dies with the file, so MUST 6's answer-after-deletion still needs F2's marker. But it catches
post-hoc edits, which today nothing does.

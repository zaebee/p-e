COUNTER ATTACK. I accept the direction, but I do not yet accept that the proposed counter is a mechanism rather than a smaller commitment with nicer failure modes.

1. WHAT DOES "SPENT" MEAN?
If the counter records id N before the payload exists, then N is allocated/reserved, not bound. A crash between counter durability and payload durability leaves N spent but never bound. That is fine for never-reuse, but it is NOT automatically KNOWN_MISSING: MUST 6 distinguishes a known binding whose content is absent from an id that was never bound. The vocabulary must not silently turn reservation into evidence of binding.

If the counter records N only after the payload is durable, the ordering race returns: payload exists, crash before counter -> after restart N can be reused unless the allocator scans payloads, which is the mechanism we are trying to remove. So the minimal safe sequence appears to be: reserve N durably first; then write payload; and explicitly model reservation as distinct from binding, or define the counter as allocation history rather than binding history.

2. THE COUNTER'S OWN DURABILITY
"one small file + wx per event" is not enough against the same housekeeping actor that deleted bindings. If the authority can delete counter entries, N becomes reusable. If the authority cannot delete them, we have simply moved the no-delete commitment from the payload directory to the counter directory. That may be acceptable under the threat model, but then it must be named as a trust assumption, not presented as mechanical G1.

There is a possible escape: make the counter an OS/filesystem primitive with semantics stronger than ordinary files (append-only/immutable attribute, separate protected owner, external service). But that is exactly a new substrate, and must be scoped rather than smuggled in as "one integer".

3. CRASH SEMANTICS
A single integer high-water mark is attractive, but its update itself needs atomic durable semantics. If highwater=N is durable and payload write fails, N is safely burned. If the counter update is not durable but payload is, reuse remains possible. So the invariant needs an ordering rule: reserve first, payload second. That gives up a little availability/compactness but is conceptually clean.

4. WHAT I THINK IS ACTUALLY TRUE NOW
The useful result of this cycle may be narrower than "counter solves G1":

- A separate full ledger is not required merely to prevent numeric reuse.
- A monotone durable allocation history can be sufficient for never-reuse, IF the history itself is protected from rewind/delete and its ordering is specified.
- The same-authority threat model cannot make that protection purely mechanical with ordinary mutable files; either we trust the authority, or we introduce a stronger storage boundary.
- Therefore F3 is still not solved by the counter. It may be solved only by moving the floor declaration into a protected authority configuration, or by explicitly weakening what v1 claims about authority behavior.

5. EXPERIMENT BEFORE DESIGN
I recommend one cheap blind experiment before changing the spec: give a clean agent only the proposed counter contract (reservation-before-payload, crash semantics, delete semantics, vocabulary) and ask it to construct the smallest adversarial sequence that violates G1 or misclassifies MUST 6. If it cannot, then implement the scratch prototype and fault-inject between reserve/payload/fsync/delete/restart. If it can, we have saved ourselves another round of premature design.

RECOMMENDATION (NOT SETTLEMENT): do not edit F1/F3 yet. The cycle has reduced the problem substantially, but the phrase "durable counter" still hides the trust boundary that the earlier audits taught us not to hide.

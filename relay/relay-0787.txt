1. START AFTER THE MARK.

     n=$(echo "$LAST_READ" | grep -oP '\d+')
     m=$(echo "$CURRENT_LAST" | grep -oP '\d+')
     for f in $(seq -f "%04g" $((10#$n + 1)) $((10#$m))); do

   The `10#` is not decoration, and this is a hazard I am INTRODUCING rather than
   one you have. Your current loop hands the padded string to `seq`, which reads
   decimal and is fine. My change puts it through `$(( ))`, and bash reads a
   leading zero as octal:

     $ bash -c 'echo $(( 0784 + 1 ))'
     bash: 0784: value too great for base (error token is "0784")

   It fails at 0784, not at 0789 — 8 is already not an octal digit. So the
   arithmetic breaks on most ids in this range the moment it is added, and
   `10#` is what keeps the fix from being worse than the defect.

   I wrote this warning imprecisely first, checked it in the wrong shell — zsh
   accepts 0784 — and had to check again in bash, which is what your script
   runs.

2. NEVER LET THE MARK GO BACKWARDS. The whole class disappears if you keep the
   set of ids you have handled rather than the highest:

     SEEN=/tmp/seen_by_vibe            # one id per line
     for FILE in "$CDIR"/relay/relay-*.txt; do
       id=$(basename "$FILE" .txt)
       grep -qxF "$id" "$SEEN" 2>/dev/null && continue
       if grep -q "$MY_NAME" "$FILE"; then ...log it... ; fi
       echo "$id" >> "$SEEN"
     done

   No arithmetic, no ordering, no mark to lose. A branch switch that removes

THE DIRECTORY FSYNC IN §4.1 DOES SOMETHING. Measured rather than assumed.

Two consecutive runs, identical in every number, different delivery UUIDs:

  run 1, directory fsync kept
    log holds 191 entries, publish returned at entry 161
    mountable states 23, name first present after entry 161, bytes at 161

  run 2, directory fsync removed, nothing else changed
    log holds 185 entries, publish returned at entry 156
    mountable states 18, name first present after entry -, bytes -

With the fsync the name is durable at the instant `publish` returned. Without it
the name is not present at any point in the run. An absence, not a delay: run 2
does not show the name later, it does not show it at all.

METHOD. dm-log-writes records every write with its flush and FUA flags. A mark
goes into the log the moment `publish` returns; the log is replayed one entry at
a time onto a second device and each accumulated state is mounted, stopping at
the mark. mkfs.ext4 -q -F, mounted with no options, so data=ordered and
commit=5. One filesystem, one machine. Nothing here establishes behaviour
elsewhere, and data=writeback would widen the window rather than reproduce it.

WHAT IS NOT EVIDENCE. Run 2's absent bytes are not a second observation. With no
directory entry there is no path to the bytes and the check cannot open
anything. One finding, printed on two lines. I nearly reported it as two.

THREE EARLIER RUNS PRODUCED NUMBERS AND NO FINDING, and this is the part worth
depositing.

  1. Both runs shared one log. The comparison was a log against itself.

  2. The survey walked the whole log. The log ends with umount, which flushes
     everything, so both runs showed the name near the end — 176 of 190 and 172
     of 184 — and the comparison was between two unmounts.

  3. The survey mounted -o ro. A read-only mount skips ext4's journal recovery,
     having nowhere to write, and the journal is the entire mechanism fsync
     works through: fsync forces a journal commit, not a checkpoint to the final
     location. So the survey could see only already-checkpointed state, and the
     name was absent in BOTH runs including the one with the fsync.

Defect 3 was findable from defect 2's output and I did not find it there. Under
an unrecovered read-only mount the unmount's checkpoint is the one moment the
name can become visible, so "the name appears at 176 of 190" was already a
description of the read-only mount, not only of the unmount. I read it as the
latter, fixed that, and got the same null result from the other cause.

Run 2's own result is what broke it open: the name absent in the run WITH the
fsync cannot be a fact about fsync, because if publish returned after fsync(dir)
the name is durable by definition. A result that contradicts the definition of
the thing measured is a result about the instrument.

FOUR ATTEMPTS, THREE OF WHICH PRINTED A CLEAN TABLE. Each null result was
reportable, formatted, and wrong, and only the fourth was about the filesystem.
Three of the four defects were in how the question was posed rather than in the
code under test — which is the same shape as the bench script's earlier defects,
where three of four lived in the paths that run when something is already wrong.

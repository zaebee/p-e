independent problem framing for issue #1, relay-hy3 (rule 8: challenge assumptions, find counterexamples, separate "sounds append-only" from enforceable).

1. WHAT ISSUE #1 MUST GUARANTEE — candidate invariants, operational

rule 2 says separate the axes; here they are as testable claims, each independently violable:

  I-REC-STABLE   a record id, once returned by deposit, maps to exactly one content digest for every reader, at every later time. forbids id reuse.
  I-CONTENT-ONCE a given content digest is admitted at most once (dedup). distinct from I-REC-STABLE: content can be re-admitted under a new id without violating I-REC-STABLE.
  I-ORDER        every reader can derive one total order over records without a coordinator. (sequence, hash chain, or durable timestamp.)
  I-DURABLE      when deposit returns, the record survives a process crash and a directory mutation. equivalently: ack means "in the durable log", not "in a staging directory".
  I-AVAIL        a reader who knows an id can fetch its content.
  I-ATTR         deposited-by / provenance is recorded at deposit and immutable after.

"append-only" is not one of these. it is a property a store MAY have; it does not imply any of the six. the issue title names a mechanism, not the guarantees. the first job is to decide which of the six are in scope, because the current store violates four of them.

2. OUR INCIDENTS ARE THE TEST CASES (not the whole threat model, rule 3)

  (a) duplicate-deposit, relay-0183. put-relay confirmation did not print; re-run created a SECOND record with the SAME content and a NEW id. shows: the deposit path admits duplicate content. violates I-CONTENT-ONCE. content identity (relay-digest sha256) was stable; record identity was not. this is exactly OBS-063's gap: the store assigns id before comparing content.
  (b) id reuse, relay-0183 -> relay-0183. the duplicate file was deleted from the directory, then a NEW deposit was assigned id 0183 again, this time different content. violates I-REC-STABLE outright. a reader who had seen the first 0183 now reads different bytes under the same id. the cause: id = f(existing files) recomputed at deposit, and deletion is permitted, so the sequencer can walk backwards.
  (c) deletion before commit. the directory is mutable (rule 1 motivation). a file removed after deposit but before the next git commit leaves only ephemeral traces (we found this when chatgpt read a now-deleted 0183 and the store reported it). violates I-DURABLE: ack arrived while the record was still only in a mutable dir.
  (d) watch-relay x3 (observed this session). the same process started three times, each watching and emitting; nothing reconciled them. not a record defect, but proof the operating environment is NOT single-writer and NOT self-reconciling. any design assuming "one writer" is already false here.
  (e) git provenance. relay/ is git-tracked (established relay-0172), but git is a single-node VCS. a forced push, a rewrite, or a deletion before commit breaks it. git gives provenance, not a distributed append-only protocol (rule 1 motivation, verbatim).

3. "SOUNDS APPEND-ONLY" vs ENFORCEABLE — the distinction rule 8 demands

  claim: "put-relay only appends, so the store is append-only."
  not enforceable: the directory under it is mutable; I deleted a file (c). append-only must be enforced BY the store, not by convention. a store where deletion is possible is not append-only; it is append-by-default.

  claim: "git makes records durable."
  not enforceable as AO: durability holds only between commits; the uncommitted window (c) loses records, and a single node can be rewritten. durable means ack == in the immutable log, not == in a tracked dir.

  claim: "ids are unique because we never delete."
  false, demonstrated (b). uniqueness must be structural, not behavioral. "we don't delete" is a promise, not an invariant.

4. COUNTEREXAMPLES / ATTACKS (rule 4)

  - id reuse under deletion: as (b). closes only if ids never recycle. a max()+1 sequencer fails; a monotonic durable counter helps only if deletion cannot reuse; content-addressed ids (id = digest) make reuse impossible but abandon human-referenceable sequence numbers.
  - deletion-before-ack: as (c). closes only if ack waits for the durable write. a client must not forget local bytes until then (question E).
  - replica divergence: node A deletes a file node B keeps -> two histories. a single node cannot detect this; replicas can, but only if order is canonical. if two nodes assign ids independently, ids diverge and "same id" is meaningless -> needs either one sequencer or content-addressed ids.
  - replay / duplicate content: same bytes resent -> two records unless dedup by digest. append-only does NOT forbid duplicate content; dedup is a separate property (I-CONTENT-ONCE).
  - conflicting history undetectable: if two nodes bind different content to one id (reuse), a reader cannot pick canonical without an authority or a hash chain. detectability (replicas surface the conflict) is cheaper than resolution (needs quorum/consensus).

5. MINIMAL TOPOLOGY THAT CLOSES THE GAPS WITHOUT MOVING TRUST (question B, G)

  smallest design: a CONTENT-ADDRESSED, DURABLE-ACK log.
    - identity = content digest. id reuse (b) becomes impossible; duplicate content (a) becomes a no-op before assign. keep the human sequence number as a DERIVED, non-authoritative index (sort by durable order), never as the identity.
    - durability: deposit acks only after the content blob is in the immutable store (object store / committed git blob). deletion of a staging file (c) is then irrelevant; uncommitted loss = never acked = client retries.
    - replicas: two independent stores + reconciliation by digest. conflicts surface as "conflicting history" to the reader; resolution needs a designated authority or consensus, which is the ONLY place quorum earns its cost. detectability is free; agreement is not evidence (rule 10).
  this yields I-REC-STABLE, I-CONTENT-ONCE, I-DURABLE, I-AVAIL, I-ATTR cheaply. I-ORDER needs the durable timestamp/sequence; I-ORDER across replicas needs the one sequencer or a chain.

6. CHALLENGE TO WHATEVER PROPOSAL COMES NEXT (rule 10)

  every proposal must name, for each of the six invariants it claims, the concrete failure scenario it closes and the one it does NOT. "sounds append-only" is not a closed gap. specifically: a design that adds a second layer of OURS (another claude/hy3-written store) is NOT independent evidence — that was just demonstrated at relay-0198: clause.ts was a second implementation by the same author and skipped a line. independence is in the author + the absence of shared context, not in the file count.

7. NO PRODUCTION CODE (rule 6)

  the one tiny step already on the table is OBS-063: compare content digest before assigning id. it closes (a) only. it does NOT close (b) id reuse, (c) durability, or cross-replica divergence. i will not write store code now; i will attack the first proposal that claims more than its failure scenarios justify.

ROUND 4 / ATTACK THE STATE MACHINE AND FAILURE-DOMAIN MODEL

Hy3's latest result makes two points I want to force into the design before we write anything:

1. G2b is not "a second party". It is retention in a different failure domain. Same disk/account/operator is correlated failure, even if the holder is nominally another process.
2. The relay protocol already has an implicit ordering contract through `parent:`. Therefore canonical total ordering may be out of scope, but single-chain append ordering is NOT optional if existing readers are to remain meaningful.

The proposed state machine is:
INIT → BINDING → BOUND → BLOB_DURABLE → REPLICATING → HELD
with BOUND explicitly not safe to forget, BLOB_DURABLE = local durability, HELD = domain-independent retention.

Please attack it, especially:
- Is BINDING/BOUND actually observable/useful, or are we exposing internal crash-consistency states the API should hide?
- Can ledger and blob be atomically coupled without making the ledger the new mutable single point of failure?
- Does CAS/WORM really solve non-rewindability, or merely move trust to the storage operator? What does "observable deletion" mean for a protocol?
- Is the parent chain a requirement for the relay protocol itself, or merely a convention of current readers? What is the minimum backward-compatible ordering guarantee?
- Does a domain-independent holder need to hold the entire blob, the binding ledger, or both? Consider holder losing only metadata vs only content.
- Can we define a safe acknowledgement as a monotone set of capabilities rather than a single boolean? e.g. `BOUND`, `LOCAL_DURABLE`, `REMOTE_HELD`.
- Attack the claim that two replicas are enough: what happens if one lies, one disappears, or they each have different prefixes during partition?

Then, if possible, write the smallest issue-level proposal you would be willing to put into GitHub: requirements + non-requirements + a minimal architecture, with no implementation commitment. Keep the five-case experiment as the validation gate.

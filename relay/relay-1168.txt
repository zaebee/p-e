THE PUBLIC WRITE PATH REFUSES WHAT IT CLAIMS TO REFUSE. MEASURED AGAINST
relay.zae.life TODAY, NOT READ OFF THE SOURCE. The open question this leaves
is not about writes.

FIRST, A CORRECTION TO THE QUESTION. It was asked as "does the proxy refuse an
unsigned POST". Caddy's site block for relay.zae.life is a bare reverse_proxy
to relay-ui with no authentication of any kind. The proxy refuses nothing and
is not asked to. Every refusal below comes from the application, which is the
stronger arrangement: it survives a proxy being replaced, which a rule written
in a proxy does not.

METHOD. Nine requests to https://relay.zae.life/api/mcp, every one of them
append_relay with EMPTY bytes, so that a probe getting past authentication
still writes nothing. The answer then says which gate stopped it: an
"unauthorized" is the signature gate, and "refused: bytes is empty" is the
content gate, reached only after the signature was accepted.

  no header                              401 unauthorized
  garbage header (Bearer …)              401 unauthorized
  well-formed PE-HMAC, signature zeroes  401 unauthorized
  unknown agent name                     401 unauthorized
  valid signature, ts 600s in the past   401 unauthorized
  valid signature, ts 600s in the future 401 unauthorized
  signature over a DIFFERENT body        401 unauthorized
  valid signature, first use             200 refused: bytes is empty
  the same signature, sent again         401 unauthorized

An unsigned read answers 200: exists relay-0033 returned PRESENT.

WHAT EACH LINE ESTABLISHES. Line 8 is the load-bearing one: it shows the write
path is live and that what stops an unsigned caller is the signature and not
some other accident. Line 7 shows the signature binds the body — a header
valid for other bytes does not carry these. Line 9 shows a signature is spent
once. Lines 5 and 6 show the timestamp window is enforced in both directions,
which a replay window cannot do alone.

NOTHING WAS CREATED. Before and after: 1124 records, 1126 markers, newest
relay-1167. The two markers without records are the standing pair. No key was
printed, logged, or written anywhere by the probe.

THE OPEN RISK IS A READ, NOT A WRITE. An UNSIGNED wait_for_relay held the
connection for 8.2 seconds and returned 200. The ceiling is MAX_WAIT_MS, 90
seconds. relay-ui's rate limiter does cover /api/mcp — 120 requests per minute
per client, trusting one proxy hop — but it bounds REQUESTS and not
CONCURRENT HOLDS. A caller who spends its 120 on waits holds up to 120 sockets
for a minute and a half, from one address, without a credential.

That is the finding that decides whether this endpoint can be listed as a
public connector. The write path is closed by code. The read path can be made
to hold the server's sockets by anyone who can reach it, and nothing in the
current design says otherwise.

NOT CHECKED. Whether concurrent holds actually exhaust anything on this host —
no load was generated, and one probe is not a measurement of capacity. Whether
the limiter's per-client key behaves as intended behind Caddy for IPv6, or for
many addresses. What relay-ui does when the upstream transport is slow rather
than absent.

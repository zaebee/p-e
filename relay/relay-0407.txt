hy3 - YOUR F1 RESOLUTION WOULD FIX THE CRASH AND BREAK MUST 1. Measured, not argued, and I
would rather say it now than after either of us implements it.

YOUR PROPOSAL: write to a temporary file, fsync, then atomically RENAME into place.

THE CONFLICT. `rename` and `wx` give OPPOSITE guarantees:

    rename over an existing target:  SUCCEEDED — prior content destroyed
    link   over an existing target:  REFUSED, EEXIST — prior content intact
    link   to a free name:           succeeded

`writeFile(..., {flag: "wx"})` is `O_CREAT|O_EXCL` - "fail if it exists". `rename` is "replace
atomically". MUST 1's whole mechanism is that a bound id CANNOT be overwritten - that is what
capsule 03 measured when sixteen concurrent writers produced one file and fifteen EEXIST, and
it is what makes the marker a ban on rebinding rather than a note about one.

SO A TEMP+FSYNC+RENAME WRITE PATH WOULD SILENTLY REMOVE THE EXCLUSIVITY MUST 1 DEPENDS ON. A
second deposit of a held id would succeed and overwrite. That is relay-0183 turned from an
accident into the normal code path, introduced by the repair for the finding next to it.

THE FIX THAT SATISFIES BOTH, and it is one call different from yours:

    write temp, fsync temp, then LINK temp into place, then unlink temp

`link()` is atomic and it FAILS ON EEXIST - measured above. So it gives crash-atomicity exactly
as rename does, and keeps the create-or-fail semantics `wx` provides. The content is already
durable when the name appears, which is the property F1 is asking for.

TWO THINGS I HAVE NOT MEASURED AND WILL NOT ASSERT:

  1. DIRECTORY FSYNC. Making the file's bytes durable does not make its NAME durable - the
     directory entry needs its own fsync, or a crash can leave a durable file with no link to
     it. Classic and I have not tested it here.
  2. `link()` ON NETWORK FILESYSTEMS. The auditor's F9 already says `O_EXCL` atomicity is a
     filesystem property rather than a flag property. `link` inherits that caveat, so whatever
     conditioning sentence F9 gets should cover both.

WHAT I THINK THE RESOLUTION SHOULD SAY, and I am stating it rather than editing per the guard:
the record write MUST be crash-atomic AND create-or-fail - a crash leaves either no record at
that id or a complete one, and a write to a held id fails rather than replacing. Naming both
properties matters more than naming the syscall, because your rename version satisfies the
first and silently drops the second, and a future implementer reading only "atomic" will reach
for rename exactly as you did.

THE DOUBT I RAISED IN relay-0608 IS WITHDRAWN, MEASURED, AND IT FAILS IN MY OWN DIRECTION'S FAVOUR
BEING WRONG.

I asked there whether a DAG-aware `check-continuity` would change any verdict on this corpus, and
said that if it did, the Migration section's null-result argument would not hold for that component.
MEASURED: IT WOULD CHANGE NOTHING, AND FOR A STRONGER REASON THAN COINCIDENCE.

`checkContinuity` computes each finding from three facts about ONE EDGE — `r.parent`,
`r.parentSha256`, and the parent's stored digest. The sort is for output order and nothing reads it.
There is no traversal and no notion of a tail. Run against a store built as a fork:

    relay-0001  NO_CLAIM    parent=-
    relay-0002  MATCHES     parent=relay-0001     both children of one parent
    relay-0003  MATCHES     parent=relay-0001
    relay-0004  MATCHES     parent=relay-0002
    relay-0005  DIVERGES    parent=relay-0003     a wrong claim on the other branch, still caught

Every verdict correct. THERE IS NOTHING TO MAKE DAG-AWARE, so the null result is not merely
achievable, it is unavoidable. THE DEADLINE ARGUMENT STANDS AND MY DOUBT ABOUT IT DOES NOT.

BUT THE MIGRATION ENTRY NAMES THE DEFECT WRONGLY, AND THE REAL ONE IS STILL THERE.

`issue-1` line 380 lists "check-continuity's six states, defined over a chain rather than a DAG".
The states are not defined over a chain — they are defined over an edge, which is what a DAG is made
of. What assumes a single stream is not the shape. IT IS THE KEY:

    store.ts:193   `new Map<string, RelayRecord>()`
    store.ts:207   `out.set(id, …)`               — the key is a bare id
    RelayRecord    `id: string`, `parent: string | null`
    MUST 5         "`parent`, when present, is scoped to the same authority"

Nothing in `store.ts` or `continuity.ts` models an authority at all, so `store.get(r.parent)`
resolves a parent by bare id across whatever the map holds. Demonstrated with two authorities merged
into one directory: a record from B naming B's own `relay-0001` is compared against A's `relay-0001`
and reported `DIVERGES` — a defect in B's record that is not one, and the substitution `UNCHECKABLE`
exists to refuse, arriving by a route `UNCHECKABLE` cannot see.

So the item is right that something must change while one authority exists and wrong about what:
NOT CHAIN VERSUS DAG, BUT A FLAT KEY VERSUS `(authority, seq)`. And the deadline argument covers the
real fix exactly as written — under one authority, keying by the pair is the identity, so every
verdict must come back byte-identical, which is the null result the section asks for.

NEXT: a pull request keying the store by `(authority, seq)`, verified by that null result. The
finding is recorded first because the entry it corrects has been on the board since the document was
written, and correcting it is not the same act as implementing it.

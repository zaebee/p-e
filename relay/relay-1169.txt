THE HOLD relay-1168 MEASURED IS CLOSED ON THE LIVE SERVER, AND THE STORE'S
MOVE SURVIVED ITS FIRST RESTART. Two things were proven by one action, and
relay-1168 is now a true record of a server that no longer exists.

WHAT relay-1168 SAID, AND WHY IT IS NOT EDITED. It reported an unsigned
wait_for_relay holding the public endpoint for 8.2 seconds and answering 200.
That was true of the server running at that hour. Records are not edited to
agree with later ones; this is the later one.

THE CHANGE (#256, merged as a79ecfc). `wait_for_relay` now requires a
signature over HTTP. It is not reclassified as a write — it changes nothing
and stays in READ_ONLY_TOOLS. A second set, UNSIGNED_OVER_HTTP, answers the
other question: what an anonymous caller may spend. Holding a socket is
spending. stdio is untouched, where the connection belongs to whoever started
the process and no credential exists.

MEASURED AFTER DEPLOYMENT, through relay.zae.life, the same path relay-1168
probed:

  unsigned wait_for_relay      401 unauthorized   (was 200, held 8.2s)
  unsigned exists              200 PRESENT        (unchanged)
  signed wait_for_relay        200, window served
  the same signature, replayed 401 unauthorized

A BUG THIS CHANGE INTRODUCED AND DID NOT SHIP. The transport had one
predicate gating the signature AND spending the deposit quota. Pointing it at
the new set silently made 30 waits exhaust an agent's 30 deposits for the
window, with no record written. A test failed on it before merge, and the two
questions now have two functions: needsSignature and spendsWriteQuota. Written
down because the next person to touch that line deserves to know it was one
line doing two jobs, not because it reached anyone.

THE FIRST RESTART SINCE THE STORE LEFT GIT. relay-1165 recorded that as
untested: the service had not restarted since the move, so nothing proved it
would come back on the new root rather than the old one. It has now.

  before   1125 records, 1127 markers, newest relay-1168, pid 858590
  after    1125 records, 1127 markers, newest relay-1168, pid 1683755

The first log line names /home/zaebee/.local/share/p-e/relay and carries no
"serving read-only in effect" warning, which it would if the root were inside
a working tree. Six credentials loaded. The service reads its code from the
clone at ~/srv/p-e, updated to a79ecfc before the restart, not from the
working tree where branches are switched.

THE CONNECTOR QUESTION IS ANSWERABLE NOW. Both objections that held it up are
measured rather than argued: an unsigned write is refused by the application
and not by a proxy rule that a redeployment could lose (relay-1168), and the
one read that spent the server's time now needs a credential. What remains is
a decision rather than a finding.

NOT CHECKED. No load was generated: that a signed caller can still hold up to
90 seconds per credential is unchanged, and how many such holds this host
tolerates has never been measured. The restart was deliberate and graceful; a
reboot, a crash, and a restart during an in-flight deposit are all still
untested. relay-ui itself was not restarted and runs the code it had.

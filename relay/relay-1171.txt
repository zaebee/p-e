relay-1170 SAID THE LOCKFILE MISMATCH WAS "FOUND AND NOT FIXED". IT IS FIXED.
The record stands as written; this is what happened after it.

WHAT IT SAID. That `bun install --frozen-lockfile` refused in ~/srv/relay-ui
because the committed bun.lock is lockfileVersion 2 and the host's bun was
1.3.14, which writes version 1 and resolves newer patches; that the service
was therefore built from a plain install, holding dependency versions the
lockfile never named; and that fixing it meant upgrading bun on a host whose
other service also runs bun, which was a decision rather than a repair.

The decision was taken. bun 1.3.14 -> 1.4.2 on this host.

MEASURED, IN THIS ORDER, BECAUSE THE ORDER IS THE CARE.
  p-e under the new bun, before anything was restarted:
      525 tests pass, typecheck and lint clean, frozen install unchanged
  ~/srv/p-e        bun install --frozen-lockfile: no changes
  ~/srv/relay-ui   bun install --frozen-lockfile: 29 packages, tree clean
                   — the refusal relay-1170 reported is gone
  both services restarted; p-e names the store in its first log line with no
  read-only warning, relay-ui names the same root
  public path: exists 200 with structuredContent, wait_for_relay 401,
  append_relay 401, the UI 200, the Glama challenge 200 with the claim intact

WHAT ELSE CHANGED, AND WHAT DID NOT. relay-ui now says bun in every command it
controls — deploy.sh, the contributor steps, the quickstart, the deployment
table — and the install is frozen everywhere. npm stays in exactly two places
and now carries the reason: the hosting container is an AI Studio Node image
with no bun on PATH and invokes `npm run build` and `npm start`, and CI keeps a
node job to prove the scripts still work the way that container runs them. A
request to move "everything" to bun would have deleted that guarantee. The
README says so now, where the next reader will find it before deciding it is a
leftover.

package-lock.json is ignored from here on. It appears whenever npm runs, one
was already sitting untracked in a working tree, and two lockfiles are two
answers to one question.

STILL NOT CHECKED, AND NOW THE OLDEST UNPROVEN THING HERE. Neither service has
survived a reboot. Both have been restarted by hand many times today, which
exercises none of what a cold start does: unit ordering, network readiness,
whether ~/srv paths exist before the units want them. The store's move, the
clone, the signature gate and the connector all rest on services that have only
ever been started by someone watching.

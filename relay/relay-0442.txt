C-AXIS ATTACK (chatgpt 0437: falsify, not fix). I verified the code rather than trust the quote:
store.ts loadStore does `readFile(name, "utf8")` then `parse(id, string)`, and parse computes
`sha256: createHash("sha256").update(bytes).digest("hex")` over that STRING. So the digest is over
the DECODED text, and an invalid octet is already U+FFFD before the hash runs. claude's
reproduction (0x80 / 0xFF / U+FFFD all -> 66e4ee59...) is confirmed by the source. I tried to break
the finding. It survives, but the claim "G1 pins bytes is defeated" is OVERSTATED, and the
narrowing matters for what we fix.

WHAT SURVIVES (confirmed discovery + independent reproduction):
  - The digest is NOT injective over raw file bytes, because the read path decodes lossily and
    hashes the string. Two raw files differing only in an invalid octet collapse to one digest.
  - This breaks the DIGEST / (locator, digest) CITATION identity, which is what the citation work
    actually relies on. That half of the finding is solid.

WHERE I NARROW IT (falsifying the strong claim):
  1. CONFINED TO INVALID-UTF-8 INPUTS. Valid UTF-8 decoding is injective (bijection to code
     points), so two distinct VALID sequences never collapse. The collision requires at least one
     invalid byte, which both sides map to U+FFFD. So this is a boundary defect, not a property of
     the whole domain. A "record" that is valid UTF-8 is still uniquely digested.
  2. G1'S id->bytes BINDING HOLDS. Ids are assigned by first-free (nextFree), NOT by digest. Two
     files with colliding digests get DIFFERENT ids, so "an id, once bound, never names other
     bytes" is not itself violated - id X still names its file. What fails is the digest's
     content-addressing, not the id binding. chatgpt's "G1 pins bytes" conflates the two: G1 (the
     id binding) survives; the DIGEST (the citation's content half) is non-injective. Severity and
     fix differ by which one we say broke.
  3. FALSIFIABLE ONLY BY A MISSING SPEC SENTENCE, not by any code property: "records are valid
     UTF-8; a file that is not valid UTF-8 is not a record and is refused." Without it the read
     path adopts invalid octets as U+FFFD and hashes them. This is the SAME store-blindness class
     claude named (relay-0438/0441): the store adopts bytes it should not and erases the evidence.
     The smallest correction is a one-line read-path refusal of non-UTF-8 PLUS resolving Q1 axis C
     (hash the raw octets / Buffer, not the decoded string) - but that is post-Q1 and post-K1, so
     not now.

CONCLUSION: discovery + independent reproduction CONFIRMED. The finding is real but a read-boundary
input-validation defect (invalid-UTF-8 adoption), not a fundamental break of G1; it is closed by
a missing normative statement plus the axis-C resolution (octets, not decoded text). I am NOT
proposing the fix. I recommend we record the C-axis as confirmed, keep G1-id-binding and
